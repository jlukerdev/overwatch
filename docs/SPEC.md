# View Protect — Prototype Specification

**Status:** Draft v0.3 (prototype). §5 corrected against the Phase 0 spikes (P0.3–P0.5) on 2026-11-13. Views amended on 2026-11-14 (spanning cells, letterboxed grid, cell gap: VIEW-1/5/7, §6 `schemaVersion: 2`). Doors screen added on 2026-11-18 (P5.6: DOOR-7…9 new, DOOR-0…6 amended, §6 `accessPolling`). The Protect interface is verified against the official v7.3.74 contract **and** against the console running 7.3.74; Access follows Ubiquiti's official API document since P5.5 and has not run against hardware (§5.2) · **Owner:** personal use only · **Built by:** coding agents (see `/CLAUDE.md`)

View Protect is a desktop app for Windows and macOS that connects to a local UniFi Protect console through the official **Integration API**. It shows live camera feeds in named, user-defined grid **Views**. It also does light UniFi Access control: unlocking the door linked to a camera, and a Doors screen that lists the console's doors with their state, their lock rules, and lockdown / evacuation.

It is **not** an NVR client. There is no playback, timeline or export, because the Protect web app already covers those.

## 2. Scope

### 2.1 Prototype (this spec)
Prove the hard parts end to end with functional UI, but no polish:
1. Connect to Protect with an API key. List cameras.
2. Create, edit, delete and switch between named grid Views, with cells that may span several grid slots.
3. Live grid that scales to the largest size that fits the window, keeping the View's aspect ratio (letterboxed).
4. Click a cell to make that camera fill the view. Escape or a click goes back to the grid.
5. Digital zoom with a reset to 100%.
6. Multi-camera cells: rotate on an interval, and/or auto-switch on motion.
7. Per-cell audio mute/unmute.
8. Unlock the Access door linked to a camera, and a Doors screen for every Access door: state, unlock, lock, lock rules, lockdown / evacuation (optional feature, off by default; DOOR-0, DOOR-7…9).

### 2.2 Deferred to MVP or later
- Auto-update, code signing and notarization
- Two-way talk (talkback)
- Multi-monitor views and kiosk/auto-start
- Exporting and importing views
- Remote access through the Site Manager Cloud Connector, for control/status/unlock only (§5.1). Video still needs LAN or VPN
- Importing Protect's own Live Views (`/v1/liveviews`) as View Protect Views
- PTZ preset/patrol buttons (the API has presets and patrols only, no continuous PTZ)
- Auto-show a camera on `nfcCardScanned` / `fingerprintIdentified` at its reader
- A per-cell motion indicator (badge) in the overlay (CELL-3; user decision 2026-11-15)

### 2.3 Out of scope
- Recording, playback, timeline and event browsing
- Any use of the private (undocumented) Protect API or username/password login

## 3. Functional requirements

IDs are referenced in `DEV_PLAN.md` and in commit messages.

### Connection (CON)
- **CON-1** The user enters a console host (IP or hostname) and a Protect Integration API key. If Access is enabled (DOOR-0), they also enter an Access API token.
  - **Settings layout** (P5.3, user request 2026-11-17; door links moved out in P5.6). Groups in this order: the keystore warning (only without a keystore, CON-2); **Console** — address and credentials, then the certificate (CON-3; the Access one only while Access is on), then the connection (CON-4/5); **Streams** (QUAL-1, the two pickers side by side). The door links, a third group since P5.3, moved to the Doors screen in P5.6 (DOOR-2, DOOR-7), so Settings has no Access group of its own. Help text is one short line at most. A **section sidebar** on the left has one link per shown group: a click scrolls to the group (smoothly unless the OS asks for reduced motion) and moves the focus to its heading, and the group in view is highlighted (`aria-current`). The groups scroll in their own container, so the sidebar stays put; at narrow widths it becomes a wrapping strip of links above them.
  - **Settings feedback** (UX polish, user request 2026-11-17). The outcome of an action (save, key save / clear, test, connect, certificate, stream defaults) is one status line — an icon and a sentence, coloured by kind — next to the control that caused it; field validation stays under its field. A stored credential shows a "Saved" check chip beside its label. Sidebar rows share the app's sidebar-item look (hover, focus ring, accent bar), and the sidebar's foot shows "View Protect v<version>". Test connection results read "Reachable. Protect version X." / "Reachable. N doors."
- **CON-2** Secrets are encrypted at rest with the OS keystore (Electron `safeStorage`: Keychain on macOS, DPAPI on Windows). They are never written in plaintext and never logged. The renderer can **write** a credential and clear it, but never read one back: it is told only *whether* one is stored (P1.5, §6.1). When the keystore is unavailable there is no plaintext fallback — Settings says so, and the key has to be re-entered next launch.
- **CON-3** TLS uses **trust-on-first-use pinning**. On first connect the app shows the certificate's SHA-256 fingerprint and the user accepts it. After that, a mismatched fingerprint blocks the connection with a clear warning. Disabling TLS verification globally is not allowed.
  - **Wording** (UX polish, user request 2026-11-17). The UI says "accepted" where it said "pinned": an Accepted / Not accepted yet chip, "This certificate does not match the one you accepted", **Replace the accepted certificate**. Behaviour is unchanged.
  - A pin belongs to one `host:port`. **Changing the console address clears the pin for the endpoint whose address changed** (P1.5), so a fingerprint accepted for one console can never be applied to a different one.
  - The app pins the fingerprint the user was *shown*: accepting re-reads the leaf certificate and refuses if it has changed in between.
  - Replacing an existing pin after a mismatch needs a second, explicit confirmation. Nothing re-pins on its own.
- **CON-4** A "Test connection" button calls `GET /meta/info` (Protect) and, when Access is enabled, lists doors (Access), then shows the versions or the error. Each half reports on its own — a working Protect key with a wrong Access token is a normal, informative result. **Nothing connects on launch unless a previous session connected successfully** and the user has not since cleared or replaced the Protect key, or moved the Protect endpoint (`console.connectOnLaunch`, §6). There is no Disconnect: the user removed it on 2026-11-17, because it stopped only the live-update feeds, not video. Resolving an address and reading a pin are offline, so a launch that does not qualify sends nothing, which keeps R9's per-key budget free for the streams. The flag is set when the devices feed first opens (a connect that *worked*, not one that only started) and cleared only by those user actions (a replaced key has to reach `open` once before a launch uses it) — an outage, a reconnect or a failed connect leaves it, and so does quitting. Even with the flag set, the launch connect still needs a host, a stored key and an accepted Protect pin; it is the same connect the user would ask for, and a failure shows as a normal connection error (CON-5). **Start screen:** Settings while there is no host; Live (the last View, VIEW-6) when the launch connect qualifies — `console.connectOnLaunch` set, a stored key and an accepted Protect pin — and at least one View exists; Cameras otherwise. It is chosen once, from the loaded state, before the launch connect has answered — so a launch connect that fails still opens on Live, where the badge and the setup notices say why, and Live says "Connecting to the console…" rather than "No cameras" until the inventory lands.
  - **Empty states** (UX polish, user request 2026-11-17). A screen with nothing to show (Live or Cameras before setup, connecting, no cameras, no Views; the app's own start-up and load failure) is a centred icon, title, one line and at most one primary action. The setup one lists four steps — console address, Protect API key, certificate accepted, connect — with the done ones ticked (`state/setupChecklist.ts`, from the same `setupGaps` rule that chooses the screen) and **Open settings**.
- **CON-5** Connection status is always visible (connected / reconnecting / error), per endpoint, outside any one screen. The phases the app distinguishes (P1.5): `disabled` (Access off, DOOR-0), `unconfigured` (no host, no credential, or an address that will not parse), `idle` (ready, nothing asked of it yet), `connecting`, `connected`, `reconnecting`, `error`.
  - **Badges** (UX polish, user request 2026-11-17). Each endpoint's badge in the header is a button that opens Settings (it starts no connect). In `error` it shows the failure reason inline, cut short with an ellipsis, with the full text in the tooltip. Phase labels are sentence case (Connected, Not set up, …). While focus mode hides the header (VIEW-4), a badge for every endpoint that is not `connected` (Access only while enabled) stays visible at the bottom-left of the Live area; nothing is shown there while everything is connected. The app version is no longer in the header; it is at the foot of the Settings sidebar.

### Cameras (CAM)
- **CAM-1** List all adopted cameras with name (fall back to model `type` when `name` is null), model, `state`, mic availability (`featureFlags.hasMic && isMicEnabled`), and a snapshot thumbnail. Thumbnails are fetched on demand — when the Cameras tab is opened and on Refresh — never on a timer. **The list loads all at once** (P4.5, user request 2026-11-16): the inventory (not when main has just pushed it, e.g. after a connect), then every online camera at once, as fast as main's one shared rate limiter lets the requests through (R9; there is no bulk endpoint). Per camera, its RTSPS feed state (QUAL-7) follows its snapshot. Until every camera has settled, success or failure, the tab shows a progress bar counting cameras ("Loading cameras…" until the inventory answers, then "Loading 7 / 18 cameras"), from the first frame, and then the whole grid appears at once; a camera whose snapshot or feed state failed still shows, with its placeholder or "Stream details unavailable". On Refresh the current grid stays up, with the progress in the header, until the new data is in, and is then swapped at once; Refresh stays enabled, and pressing it during a load supersedes that load, whose replies are then ignored. An inventory that empties during a load abandons it, and the cameras that come next load all at once again. Live `state` changes from the devices feed (CAM-2) still update a card at once, during a load too, and a camera that comes back online (CAM-3) or is added afterwards fetches its own thumbnail and feed state, which fill in on their own. **The thumbnails are one shared cache** (P5.2): a renderer store that outlives the tab, which the View editor also reads and fills (VIEW-3), so an image either screen fetched is reused by the other. It is kept in step with the inventory whether or not the tab is open: a camera that goes offline or leaves loses its image (CAM-3), and an inventory that empties clears it. The editor fetches snapshots only, never feed states (QUAL-7 says how the tab fills those in). Every open of the tab still reads the inventory and reloads every camera; once a load has completed, a re-open behaves like Refresh — the last grid stays up with the progress in the header and is swapped at once when the new data is in — and only an open with nothing loaded yet shows the full loading card.
  - **Cameras screen look** (UX polish, user request 2026-11-17). The header shows the count as "N cameras" and Refresh (no Settings button; the app nav has one). A card leads with its thumbnail edge to edge, then the name, a state dot and label, a microphone icon for an audio source, the model as a quiet line, and the RTSPS chips (QUAL-7). An offline card shows a camera-off icon and "Offline" on a dimmed thumbnail. The first load is a centred loading state, not a card.
- **CAM-2** Camera state stays current through `/v1/subscribe/devices`: `state` changes, renames, adds and removals.
- **CAM-3** A cell whose camera is not `CONNECTED` shows an "Offline" (or "Connecting…") placeholder and resumes on its own when the camera comes back. The contract says the snapshot endpoint returns 503 for offline cameras; treat that as normal, not an error. **Unobserved:** every camera was online throughout P0.3, so the 503 path was never seen (R11). Tolerate either a 503 or some other failure for an offline camera.
  - **Placeholder look** (UX polish, user request 2026-11-17). The placeholder is a centred icon and label: a spinner for "Connecting…" / "Camera connecting…", a camera-off icon for offline, an alert icon for the video service restarting and for stream errors. While a stream is connecting, a snapshot already in the shared thumbnail cache (CAM-1) is drawn dimmed and blurred behind the spinner and label. Nothing is fetched for it and no timer is used; it is never shown for a camera that is not online, and never without the "Connecting…" treatment over it, so it cannot be mistaken for live video. In small cells the label shrinks, then hides, leaving the icon with the text as its tooltip.
- **CAM-4** For doorbells with `hasPackageCamera`, the package camera can be put in a cell as its own source (`<cameraId>:package`). **Unverified:** the development network has no doorbell, so nothing with `hasPackageCamera` was exercised (P0.3 §2).

### Views (VIEW)
- **VIEW-1** A View has a name, a `cols × rows` slot grid (each 1–4) and cells that each cover a rectangle of slots. Together the cells **tile the grid exactly**: no gaps and no overlaps; an empty slot is a cell with no cameras. Presets: 1×1, 2×2, 3×2, 3×3, 4×3 and 4×4 (all 1×1 cells), plus spanned presets such as **"1 + 5"** (3×3 with a 2×2 cell top-left) **"1 + 7"** (4×4 with a 3×3 cell top-left) and **"2 + 8"** (4×4 with two 2×2 cells across the top). Custom sizes go up to 4×4. The editor merges a selected rectangle of whole cells into one cell, or splits a spanned cell back into 1×1 cells (P3.3).
- **VIEW-2** Each cell holds zero or more cameras (see CELL).
- **VIEW-3** The user can create, rename, duplicate, delete and reorder Views. A view editor assigns cameras to cells with drag-and-drop or a picker.
  - **Side panel, dialogs and drop hints** (UX polish, user request 2026-11-17). The editor's right column is a tabbed panel, **View | Cell** (arrow keys, Home / End move between tabs), over the camera palette, which stays visible under both. The View tab holds the Display and Quality groups, one control per line; the Cell tab is the inspector for the selected cell. Picking a cell while nothing is selected opens the Cell tab; `Esc` (outside a field or dialog) clears the selection. Leaving with unsaved changes and Delete ask in the app's own dialog ("Discard unsaved changes?" — Discard changes / Keep editing; `Delete "<name>"?` — Delete View / Cancel), not an OS box; an answer is ignored if the View went away meanwhile. (Closing or reloading the window still asks through main's native box.) An empty cell shows a plus and "Drop a camera" (the plus alone when small), the drop target is tinted and ringed, and a View with no cameras says so in the palette. Each palette entry shows a 16:9 thumbnail from the snapshot cache — read only, nothing is fetched for the palette — or a camera icon. A toolbar button that cannot act says why in its tooltip.
  - **Editor (P3.3).** Opened from the View switcher ("Edit View" for the active View, "New View" for a new empty 2×2 one named "View N"); while it is open the Live grid and the `1`–`9` shortcuts are off. It edits a **draft** of one View: name, layout (a preset, or columns × rows 1–4 through `resizeGrid`), `aspect` (16:9, 4:3, 1:1, 9:16, 21:9 or a custom whole-number `w:h`), `gap`, `fit`, grid quality and fill quality (QUAL-2/5), and the cells. Nothing is stored until **Save**; **Discard** goes back to the stored View, and leaving or switching to another View with unsaved changes asks first — as does going to another screen or closing / reloading the window. The editor stays open across a visit to another screen: coming back to Live reopens it on the same View (the unsaved draft is gone once the user agreed to leave). New, duplicate (disabled while the draft has unsaved changes), delete (confirmed) and reorder act on the stored list at once.
  - **Editor layout (P3.8).** Each action sits by what it acts on. The Views list has reorder up/down on each row and a footer pinned under it: **New View**, then **Duplicate** and **Delete** under a "This View: <name>" caption. The header holds the name, the Grid controls (layout, columns, rows) and, at the far right, **Close**. The other settings are in the side panel's **View** tab, in two titled groups (see "Side panel" below; until 2026-11-17 all three groups sat above the canvas): Display (aspect, gap, fit, show camera names — VIEW-8) and Quality (grid, fill). Above the canvas, the selection toolbar has **Merge**, **Split** and **Clear cameras** at its far left, followed by how many cells are selected (order changed at the user's request, 2026-11-17, P5.2). Under the canvas, a save bar that is always shown (so the canvas never jumps) gives the draft's state ("Unsaved changes" with an amber dot, "All changes saved", or the last error) with **Discard** and **Save**. App-wide, buttons carry an icon and a colour for their kind of action: accent-filled for a screen's main action (Save, Connect), red for a destructive one (Delete, Clear), quiet for low-emphasis ones (Close, Discard, reorder).
  - **Cells.** Click a cell to select it; drag across cells or shift-click to select a rectangle, which grows to take in any cell it cuts through, so a selection is always mergeable. **Merge** keeps the first cell in reading order that has cameras (VIEW-1, `mergeCells`) and says how many other cells lost theirs; **Split** turns a spanned cell back into 1×1 cells. Picking a different preset carries the cells that have cameras, with their settings, onto the new cells in reading order and says how many did not fit.
  - **Cameras.** Drag a camera (or a doorbell's package camera, CAM-4) from the palette onto a cell to make it that cell's only camera; drag one cell onto another to swap their contents. The inspector for a selected cell lists its cameras in order, with add, remove and move up/down — with two or more, the Live screen rotates through them in this order when the cell has a rotation interval and switches on their events when its motion switch is on, otherwise it stays on the first (CELL-2), as the note under the list says — and the cell's quality override (QUAL-3).
  - **Snapshots (P5.2, user request 2026-11-17).** A cell with a camera shows that camera's snapshot behind its name chip, so the user can see what it looks at: when a camera is dropped or picked into a cell, and in every cell with a camera when an existing View is opened in the editor (and after a swap, a merge, a split or a layout change). A multi-camera cell shows only the camera at the head of its list; a package ref (`<id>:package`) shows the package channel (`channel=package`, CAM-4). The image is fitted with the View's `fit`, and it never takes the pointer, so selecting, dragging the chip and dropping work as on a text-only cell; the selected and drop highlights stay visible over it. The images come from the Cameras tab's shared cache (CAM-1): a cached image is shown at once, **whatever its age**, and only a camera with no entry is fetched — through the same `snapshot` call and main's shared rate limiter (R9), default quality (never `highQuality`), the snapshot only (no feed-state GET, QUAL-7), never on a timer, and no stream is opened (QUAL-8). A camera that a Cameras-tab load in flight covers is left to that load (while the load is still reading the inventory, every camera waits for it). A camera whose cached answer is `failed` or `unavailable` is tried **once more each time the editor opens** (on a View: switching Views in the editor counts as opening it); while it stays open, a failure is not retried, so nothing loops. A fetch the editor makes lands in the shared cache, so the Cameras tab reuses it; Refresh there still refetches everything. Package-channel snapshots are cached separately, by the same rules, and only the editor asks for them. A missing camera, an offline one, a package ref to a camera without a package camera, and a snapshot that is still loading, unavailable or failed keep the text-only cell with its label.
  - **In use (P5.2, user request 2026-11-17).** A palette entry whose exact ref heads at least one cell of the draft (its first camera; a camera only later in a cell's list does not count, and a doorbell's camera and its package camera are judged separately) shows a green check mark at the right (replacing the first "In use" pill, user decision 2026-11-17; "In use in N cells" as its tooltip and accessible text) with a slightly quieter label; it stays draggable and updates with every edit of the draft.
  - **Multi-camera settings (P4.2).** For a cell with two or more cameras, the inspector shows a "Multi-camera" group with the cell's CELL-2 settings (hidden for fewer, where they do nothing; they stay stored in the cell): **Rotate every N s** (a checkbox, off by default; turning it on starts at 10 s, or at the cell's last interval if Rotate was unticked earlier in this editor session, since unticking removes the interval from the cell; the input is 5–86400), **Switch on events** (off by default), and, while that is on, the **Triggers** (Motion, Smart detection, Ring; all checked by default), the **Smart detection types** filter while Smart detection is checked (the types the cell's cameras report, plus any the cell already has; all of Person, Vehicle, Package, License plate, Face, Animal when no camera reports any; known types first in that order, then others under their own name; none checked = any type — a type from a newer console is kept), and the **Hold** after the event ends (0–86400 s, default 15). The 86400 s (one day) caps are the inputs' own, not the schema's: a stored larger value is kept unless the user edits that field. A number input commits while typing only once the number is in range, and clamps it on leaving the field. Like every other setting they edit the draft: saved with Save, reverted by Discard. Nothing is turned on for the user.
- **VIEW-4** The active View is chosen from the View switcher, a sidebar on the Live screen that lists every View in order; the first nine show their number. Keyboard: while the Live screen is open, `1`–`9` (top row or numpad with Num Lock on, by physical key so any layout works) select View N if it exists. The shortcut is ignored with any modifier held (Ctrl, Cmd, Alt or Shift), on auto-repeat, while typing in a text field, select or editable element, and when something else already handled the key. Selecting a View stores it as the last View (VIEW-6); selecting the one already showing does nothing. (P3.2)
  - **Collapse and focus mode** (UX polish, user request 2026-11-17). The switcher has a collapse toggle: collapsed it is a slim rail showing each View's number (a dot from the tenth on) with the name as tooltip and accessible name, and icon-only New View / Edit View. The choice is remembered per machine in the renderer's localStorage, not in the config. **Focus mode** hides the app header and the View switcher so the wall has the whole window: the switcher's focus-mode button or `F` toggles it (`F` has the same guards as `1`–`9`). It applies only while Live is showing with the editor closed; leaving Live or opening the editor ends it, and it is session-only, never stored. An "Exit focus mode (F)" control at the bottom-left of the Live area appears on pointer movement and hides after `ui.overlayAutoHideSec`; it stays in the tab order and shows on keyboard focus. `1`–`9` still switch Views (a failed switch shows as a pill over the top of the wall), `Esc` never exits focus mode, and CON-5's indicator stays on screen for any endpoint that is not connected.
  - The list scrolls on its own; **New View** and **Edit View** are pinned to the bottom of the switcher, always in view (P3.8).
  - **No Views yet:** the Live screen offers "Create a View", which makes **View 1** showing the cameras in the camera list's order, one per cell, on the smallest uniform preset (1×1, 2×2, 3×2, 3×3, 4×3, 4×4) with a cell for each — at most 16; cells past the last camera stay empty. The editor (P3.3) changes it from there.
  - A one-camera cell shows its camera; a cell with several shows the one its scheduler picks (CELL-2), its **first** until the scheduler says otherwise. A cell whose camera is no longer on the console is drawn empty with "Camera not found" and its id, and asks for no stream; it plays again if the camera comes back (CAM-2). Likewise a `<cameraId>:package` cell whose camera has no package camera (`hasPackageCamera` false) is drawn empty with "No package camera" and the camera's name, and asks for no stream; it plays again if the flag comes back (CAM-4).
- **VIEW-5** The grid is scaled to the largest size that fits the window and centred horizontally or vertically, so that a 1×1 cell has exactly the View's video aspect ratio, `aspect` (per View, default 16:9). The leftover band is background. `aspect` is a View setting rather than read from the cameras because the Integration API does not report a camera's resolution: the `camera` schema in the contract has no width or height. A camera whose own shape differs from `aspect` (e.g. a doorbell) is fitted inside its cell by the View's `fit` (`contain` by default, `cover` as an option). The layout reflows on resize with no scrollbars.
- **VIEW-6** Views and settings are stored locally as versioned JSON and survive restarts. The app reopens the last active View.
- **VIEW-7** Each View has a `gap` in px (0–64, default 0) between adjacent cells only, with none at the outer edge. With unit cell `w × h` and gap `g > 0`, a cell spanning `k` slots is `k·w + (k−1)·g` wide and `k·h + (k−1)·g` tall, so it cannot match `aspect` exactly while the 1×1 cells do. The app keeps the 1×1 cells exact; the spanned cell's few px of difference is taken up by `fit` (e.g. ≈3.5 px of height for a 2×2 cell with an 8 px gap at 16:9). Accepted by the user on 2026-11-14.
- **VIEW-8** Each View has `showNames` (default on): whether its cells draw the camera's name over the picture (CELL-3), in the grid and in fill. Set in the Display group of the View editor's View tab with a **Show camera names** checkbox, saved with the draft like the other View settings. Off, a cell has no name chip; a "Camera not found" / "No package camera" placeholder still shows its label, which is not the name overlay. (P4.3, user request 2026-11-16)

### Cells (CELL)
- **CELL-1** A cell with one camera shows that camera live.
- **CELL-2** A cell with several cameras is a **multi-camera cell** with:
  - `rotateIntervalSec` (optional, ≥ 5): cycles through its cameras in order.
  - `motionSwitch` (on/off): when a camera in the cell reports a trigger event, the cell switches to it.
  - `motionTriggers` (default `["motion", "smartDetect", "ring"]`): which event types count. `smartDetect` covers `smartDetectZone`, `smartDetectLine` and `smartDetectLoiterZone`.
  - `smartDetectTypes` (optional filter, e.g. `["person", "vehicle"]`): only smart detections with these types trigger.
  - `motionHoldSec` (default 15): how long a triggered camera stays shown **after the event ends** before rotation resumes, measured from the event's `end` **timestamp** and not from when the `update` carrying it arrives (that update lags 3–5 s, §5.1), so the camera is held for 15 s after motion actually stopped (G4). If no `end` arrives within 60 s, treat the event as ended.
  - Priority: `ring` beats any other trigger. Otherwise the most recent event start wins. Ties go to the earlier position in the list.
  - The scheduler (`features/cells/cellScheduler.ts`, P4.1) resolves the details:
    - **Clock skew.** An event's `add` records `offset = arrival − start`, the console→local clock skew (plus the add's small delivery lag). Its `end` is placed at `end + offset` in local time, clamped to when the update arrived, and the hold runs from there. An event first seen already ended (connected mid-event) has no offset: its end is `min(end, arrival)`.
    - **Stale.** An event with no `end` 60 s after the app first saw it is treated as ended at that moment, and the hold applies after it. Later messages for that id are ignored. An event whose hold is over is remembered for 5 minutes, then forgotten. After that, a message for an id the app doesn't know is ignored if its `start`, corrected by the latest `add`'s offset, is more than 5 minutes old, or more than 60 s old when it has no `end` (it would already be stale). Until an `add` has supplied an offset these checks are skipped, so a console whose clock is minutes behind still triggers.
    - **Ends after the hold.** A different `end` for an event whose hold is over, or that next / previous dismissed, does not bring it back. A different `end` for an event still running or held is recomputed.
    - **Changing `motionHoldSec`** in the View editor re-applies the new hold to every ended event, measured from its end, whether or not the old hold had already run out.
    - **When the last trigger is over**, rotation resumes from the camera that was held, with a full interval. Without rotation the cell stays on that camera.
    - **Manual next / previous** steps from the camera on screen, dismisses the triggers active at that moment (newer events still switch the cell) and restarts the interval. While filled it only changes the pinned camera (FILL-3).
    - **Exact camera ids.** An event triggers a cell only if its camera id is exactly one of the cell's, so a `<cameraId>:package` entry (CAM-4) is not triggered by `<cameraId>`'s events.
    - **Missed intervals** (sleep, a long pause) step the rotation once and reschedule from now; they do not spin through the cameras.
    - An empty `smartDetectTypes` filter is no filter. The filter applies to `smartDetect` events only, never to `motion` or `ring`.
  - **Wiring (P4.2).** Main forwards each motion, smart-detect and ring event over `vp:event/cameraEvent`, repeats included. The renderer's event bus (`state/eventBus.ts`, created at startup) stamps each with its local arrival time, hands it to every multi-camera cell on screen that it matches, and keeps, per event id, the first message and the latest one with a different `end` for **5 minutes** after the id's last message (at most 500 ids). Each grid slot whose cell has two or more cameras gets a scheduler (`features/cells/schedulerSet.ts`), keyed like the slot by the cell's **first** camera, so rotation never remounts the cell; a View edit or a View switch that keeps the key reconfigures it, keeping the camera on screen by id.
    - **Mounted mid-event.** A scheduler created later — a View switch, the Live screen coming back from Settings or the editor — replays the retained events at their **original arrival times** with rotation off, then switches rotation on with a full interval from the moment it mounted. So a trigger still active shows at once, its hold measured from when the event really ended; one whose hold ran out before mount does not, and the cell starts where it would be had it been on screen without rotation: its first camera, or the camera that was last held.
    - **A missing camera** (no longer on the console, CAM-2, or a package ref without a package camera, CAM-4) in a multi-camera cell takes its turn in the rotation drawn as "Camera not found" / "No package camera": the scheduler runs over the View's `cameraIds` as stored, and the cell plays again on the next camera.
  - **Pre-warm (P4.4).** 2 s before a rotation step, the cell opens the next camera's stream in a hidden player, at the quality it will play at once shown (the cell's grid quality, or the package channel for a package ref). At the step, that player is shown as is, so the cell switches to a picture that is already decoding instead of "Connecting…". If the step is cancelled before it happens (a trigger breaks in, or the user steps), the hidden player is closed, unless what replaces the step shows that same camera: a manual step or a trigger onto the pre-warmed camera uses it as is. There is no pre-warm for trigger switches or manual steps (nothing is known in advance), for a filled cell (it is pinned, FILL-3), for the cells under a filled one or a grid drawn at zero size (a minimised window: nobody sees them), for a camera that would be drawn as missing (it asks for no stream), or for the same camera's other channel (that switch is the player's own seamless quality swap, QUAL-6). Cost: one extra stream per rotating cell for about 2 s of each interval.
  - **Setup requirement (P0.3 §5):** `motion` events only arrive for cameras whose **motion detection is enabled in Protect** — it was off on all 9 development cameras, which is why the first runs saw no `motion` at all. It is independent of smart detection: with both on, one walk-by produced both `motion` and `smartDetectZone` events. The Integration API exposes no motion-detection flag on the camera object, so the app cannot detect this or warn about it. The default trigger set (`motion`, `smartDetect`, `ring`) covers cameras with either setting on; document the per-camera Protect setting as user setup.
  - This matches Protect's own Live View slot model (`cycleMode: motion | time`, `cycleInterval`), with one difference: View Protect lets a cell use **both** at once (rotate on a timer and break in on motion).
- **CELL-3** The overlay shows the camera name (unless the View hides names, VIEW-8), a mute toggle (only if the camera has a mic), an unlock button (only if Access is enabled and a door is linked), and for multi-camera cells the position (e.g. `2/4`) with manual next/previous buttons. A motion indicator was part of this requirement; it is deferred to after the prototype (§2.2, user decision 2026-11-15).
  - The camera name sits top-left and is **always visible** when the View shows names (VIEW-8). Everything else is in a controls strip, top-right, that auto-hides (CELL-4). The controls arrive task by task: the back control while filled in P3.5 (FILL-1), the "100%" zoom reset while filled and zoomed in P3.6 (ZOOM-2), the quality picker in P3.7 — the cell's own in the grid (QUAL-4), the fill picker while filled (QUAL-5), none on a package-channel cell (CAM-4) — the position and next/previous in P4.3, mute (and the fill volume) in P5.1 and unlock in P5.4. A click on a control is only that control's; a click anywhere else on the cell, the name and badge included, is a click on the cell (FILL-1).
  - **Strip order** (user's call, 2026-11-16), left to right. In the grid: position and next/previous, the mute toggle (AUD-1), then the cell's quality picker. In fill: the zoom reset (ZOOM-2), the back control, position and next/previous, the mute toggle and the volume slider (AUD-3), then the fill quality picker, with its icon-only Save button just after the select. Mute and volume, where the camera has audio, sit together just before the picker (P5.1). The effective quality badge (QUAL-7) comes last and only on a cell with **no** picker — a package-channel cell, which shows `PKG` — because a picker's select already shows the quality playing, in the same per-quality colour.
  - **Position and next/previous (P4.3).** A cell with two or more cameras has, in the strip just before the quality picker, a "Previous camera" button (‹), the position of the camera shown (`2/4`, tooltip "Camera 2 of 4") and a "Next camera" button (›). They show on hover and auto-hide with the rest of the strip (CELL-4), in the grid and while filled. A press steps the cell's scheduler as described under CELL-2's **Manual next / previous**, and never fills the cell; the position between the buttons is part of the control, so a click on it does nothing either. A one-camera cell has none of them. A step while filled also resets the zoom to 100%: the next camera starts at 1×, like a freshly filled one (ZOOM-2).
  - A multi-camera cell whose shown camera is missing (drawn "Camera not found" / "No package camera", CAM-2/4) keeps the same position and next/previous controls over its placeholder, which is drawn as a centred camera-off icon and label, the same composition as an offline cell (no name chip, no quality badge, not fillable by a click), so a cell that does not rotate is never stuck on a missing camera. A filled multi-camera cell whose shown camera is missing — a step landed on it, or the camera left the console while filled — stays filled, drawn as that placeholder with the back control and then the step controls in its strip, and leaves by back, `Esc` or a plain double-click like any filled cell; the next step plays the next camera, still filled. A one-camera cell whose camera leaves the console still leaves fill (FILL-1).
- **CELL-4** Overlay controls show on hover and auto-hide after 3 s of no mouse movement.
  - **Overlay look** (UX polish, user request 2026-11-17). The overlay's chips share one look: a dark translucent backing, 28 px tall, buttons at least 28 × 28 px. The one exception is a quality-coloured select, which keeps its opaque tinted background (QUAL-7; user decision 2026-11-16). While the strip is shown a soft gradient darkens the top of the picture and fades with it. In a cell too narrow for the name and the strip side by side, the strip wraps under the name.
  - The delay is `ui.overlayAutoHideSec` (§6, default 3); every movement restarts it, and leaving the cell hides the controls at once. The cursor hides with them while it rests over the cell and comes back on the next movement. Keyboard focus inside the strip shows it and keeps it shown, so the controls can be reached by Tab; focus from a mouse click does not.

### Stream quality (QUAL)
Protect offers `high`, `medium` and `low` RTSPS streams for every camera, plus `package` on doorbells. **No quality is hard-coded.** The user picks it at each level below, and the most specific setting wins.

- **QUAL-1** App settings set two defaults: **grid quality** (default `low`) and **fill quality** (default `high`). They are set on the Settings screen's **Streams** card: each select saves on change (`vp:streams/defaults`) and shows a failed save under itself. They cannot be changed during a perf run, while the renderer is shown the run's quality as the grid default (P3.7).
- **QUAL-2** A View can override grid quality for all its cells (`gridQuality`).
  - Set in the Quality group of the View editor's View tab: **Grid quality** and **Fill quality** (QUAL-5) selects, each "App default (X)" — X naming the current app default, e.g. `LOW` — or High / Medium / Low. Saved with the rest of the draft. The inspector for a selected cell has the same select for the cell's `quality` (QUAL-3), with "View default (X)".
- **QUAL-3** A cell can override quality (`quality`). Effective grid quality = `cell.quality ?? view.gridQuality ?? settings.defaultGridQuality`.
- **QUAL-4** The cell overlay has a quality picker (Low / Med / High). Changing it updates that cell's `quality` and saves it. "Use View default" clears the override.
  - A compact select in the overlay's strip (CELL-3) of a grid cell: "Default (X)", where X is what the cell plays with its override cleared (`view.gridQuality ?? settings.defaultGridQuality`), then High / Medium / Low (the option was "View default (X)" until 2026-11-16; the View editor's inspector keeps "View default (X)", where the longer name has room). It shows the cell's own override, "Default" when there is none. Its text and border take the colour of the quality the cell plays (QUAL-7). A pick is saved at once to that cell of the View and swaps seamlessly (QUAL-6); a save that fails is logged and the picker shows the stored value again. A package-channel cell (CAM-4) has no picker: the package channel is a source, not a quality.
  - While the select has focus — including the focus a click gives it, since its dropdown is then open — the strip does not auto-hide (CELL-4). A pick made with the mouse hands the focus back, and the strip then hides on the usual delay. A select focused with the mouse also hands the focus back when the pointer leaves the cell, or on `Esc` while its dropdown is closed (the next `Esc` then leaves fill), so a dropdown closed without a pick never pins the strip. Keyboard focus stays where it is. Pressing or using the select never fills the cell, pans the zoom or triggers the `1`–`9` shortcuts or fill's `Esc`.
- **QUAL-5** Filled mode uses `view.fillQuality ?? settings.defaultFillQuality`. The fill overlay also has a quality picker, which applies until you leave fill mode; it has a "save as default" option.
  - While filled, the strip's picker is the fill picker instead of the cell's: High / Medium / Low, showing what the filled camera plays, coloured per quality (QUAL-7). A pick is not stored: it applies to this fill only and is dropped on every way out of fill (Esc, back, double-click, a View switch, the camera or cell going away) and when another cell is filled, so filling again starts from the View's fill quality.
  - "Save as default" is a **Save** button just right of the fill picker (the user's call, 2026-11-15; labelled "Save for this View" and left of the picker until 2026-11-16, now an icon-only save button with the tooltip "Save as this View's fill quality"): it sets this View's `fillQuality` to the quality shown, and the pick is dropped once saved (it now equals the stored one) — unless a different pick was made while the save was in flight, which is kept. It shows only once a pick has changed what plays, i.e. the quality shown differs from what the View fills at without a pick (`view.fillQuality ?? settings.defaultFillQuality`). The app-wide fill default is changed only in Settings (QUAL-1). A package-channel cell has no fill picker and stays on the package channel (FILL-2).
- **QUAL-6** Changing quality swaps seamlessly: the current stream keeps playing until the new one renders its first frame (same mechanism as FILL-2).
- **QUAL-7** The app shows the effective quality on hover, and in the camera list shows which RTSPS qualities exist on the console (P3.7), as small chips (HIGH, MED, LOW) with the missing ones dimmed, "No RTSPS streams created yet" when there are none, "Checking streams…" while loading, and `PKG` only for a camera with a package channel. It is fetched with the thumbnails — alongside them, in the same all-at-once load (CAM-1, P4.5), on demand, again on Refresh, never on a timer, per camera straight after its snapshot, never for an offline camera, and not for a camera whose snapshot failed with a list-level error (bad key, unpinned certificate, rate limit), which reads "Stream details unavailable" at once — and is a `GET rtsps-stream` only: it never creates a stream (that is QUAL-8's `ensureStream`). The renderer gets booleans, never URLs. A failure reads "Stream details unavailable", not an error. A quality a cell creates later shows after the next Refresh. A thumbnail the View editor fetched (VIEW-3, P5.2) comes without its feed state: the editor never asks for one. While the Cameras tab is open between loads, such a camera has its feed state fetched on its own (one GET, no second snapshot); otherwise the tab's next load or Refresh fetches it with the rest. Until then its row shows nothing for RTSPS, never a "loading" that does not end.
  - On hover, in the cell's strip (CELL-3): a cell with a quality picker shows the quality in the picker itself — the option selected (e.g. "Default (LOW)" or "Medium") — with the select's text and border coloured per quality (HIGH green, MED amber, LOW blue). A cell without a picker, the package-channel cell (CAM-4), shows a badge instead, `PKG` in violet, last in the strip. There is no separate badge beside a picker (the user's call, 2026-11-16: it repeated what the picker says).
- **QUAL-8** RTSPS URLs are created **on demand**: the first time any cell or fill view needs a quality for a camera, main GETs the existing streams and POSTs only the missing quality. The app never deletes streams (they may be shared with other integrations).

### Focus / fill (FILL)
- **FILL-1** Clicking a cell (outside the controls) fills the grid area with that camera. `Esc`, a click on the back control, or a double-click returns to the grid.
  - **Transition** (UX polish, user request 2026-11-17). Filling and returning animate for about 170 ms: the cell grows from, or shrinks to, its grid position, scaled uniformly so the picture is never stretched, as one compositor transform on the slot (the player is not re-created or moved, FILL-2). No animation under `prefers-reduced-motion` or on a View switch, and every way out still acts at once. **Perf not re-measured**: P2.5 needs a real console (docs/perf-results.md).
  - Filled means the **whole grid area** (everything the View's letterboxed grid can use). The app header — with the connection badge and any error — and the View switcher stay visible and usable beside it, unless the user has turned on focus mode (VIEW-4), which hides both by the user's choice while `Esc` still only leaves fill; picking another View there returns to the grid like `1`–`9` does. Only a camera cell fills; an empty cell or one drawn as "Camera not found" / "No package camera" does nothing when clicked (a filled multi-camera cell stays filled on one, FILL-1, CELL-3). Only a plain primary click fills: a click with Ctrl, Cmd, Alt or Shift held does not. A camera cell shows a pointer cursor in the grid (it still hides when idle, CELL-4).
  - The filled view keeps the cell's overlay (CELL-3/4): the name (VIEW-8), and the auto-hiding strip — left to right, the zoom reset (ZOOM-2), then a **back control** shown as a 2×2 grid icon (labelled "Back to grid", Esc in its tooltip), the position and next/previous of a multi-camera cell, the mute toggle and volume slider of a camera with audio (AUD-1/3), and the fill quality picker (QUAL-5) with its Save button, whose select shows the fill quality coloured per quality (QUAL-7). A package-channel cell has no picker and shows its `PKG` badge last instead. (The back control sat top centre, apart from the strip, until the user moved it into the strip on 2026-11-16.)
  - `Esc` returns to the grid unless it is held down (auto-repeat), pressed with a modifier, typed into a text field, or already handled by something else. A double-click returns only **without** a modifier: modifier + double-click is reserved for ZOOM-2's zoom reset. A double-click on a grid cell fills it and stays filled — it does not fill and then immediately return: a double-click returns only if its first click arrived while already filled.
  - Switching View (`1`–`9`, VIEW-4) returns to the grid, as does its cell no longer existing, or — for a one-camera cell — the filled camera leaving the console (its cell becomes "Camera not found", CAM-2). A **multi-camera** cell instead stays filled on its "Camera not found" / "No package camera" placeholder, whether a next/previous landed there or the shown camera left the console while filled (user decision 2026-11-15): the placeholder keeps the back control, the next/previous controls, `Esc` and the plain double-click to leave, and a step onto a camera plays it, still filled (CELL-3). Coming back to that View later shows the grid, not the fill.
  - The camera is fitted with `contain` in fill whatever the View's `fit`, so the whole picture is visible; detail is what zoom is for (ZOOM-1).
- **FILL-2** Filled mode switches from the cell's grid quality to the fill quality (QUAL-5) if they differ. The switch should look seamless: keep the grid stream playing until the first frame of the fill stream renders.
  - The filled view is the **same player** as the cell, enlarged — not a second one. Its quality changes to the fill quality, which is the player's own seamless swap (QUAL-6); returning to the grid swaps back the same way. A package-channel cell (CAM-4) stays on the package channel in fill.
  - The rest of the grid stays mounted underneath, covered but **still streaming** (NFR-2 budgets 10 grid streams plus 1 fill stream), so returning to the grid is instant. While covered, its cells can't be reached by Tab or assistive tech.
- **FILL-3** A filled multi-camera cell pins the current camera (no rotation) until the user returns to the grid.
  - The scheduler's `pin` implements it (`cellScheduler`, P4.1): it freezes the camera on screen, a trigger's included, until `unpin`; events are still recorded meanwhile, so on return to the grid a trigger still active shows, otherwise rotation resumes from the pinned camera with a full interval. Wired to fill in P4.2: the filled cell's scheduler is pinned in the same render that fills it, so it never changes camera on its own while filled (the user's next/previous still steps it, CELL-3), and unpinned on every way out of fill (Esc, back, double-click, a View switch, the slot going away) or when another cell is filled. It stays pinned, and filled, while the camera it shows is missing (FILL-1, CELL-3).

### Zoom (ZOOM)
- **ZOOM-1** Digital zoom works in filled mode: mouse wheel or pinch zooms at the cursor (1×–8×), and drag pans.
  - **Fill only.** Grid cells never zoom or pan: a wheel over the grid does nothing, and a click there still fills (FILL-1). "Optionally in cells" is settled as not built, by the user's choice on 2026-11-15.
  - The wheel and a trackpad pinch zoom about the point under the cursor, which stays put, between 1× and 8×. Chromium delivers a trackpad pinch as a Ctrl+wheel, so a Ctrl+wheel zooms the camera too, a little faster per event than a plain wheel, and never zooms the app's page. On a touch screen two fingers pinch about their midpoint, and moving them pans.
  - A drag pans only while zoomed in; at 1× there is nothing to pan. The pan is clamped to the cell: the zoomed picture always covers the whole filled area, so it can never be dragged past an edge. Resizing the window keeps the zoom level and re-clamps the pan.
  - A drag is not a click: a press that moves more than a few px never counts as a click on the cell, so panning never starts fill's double-click return (FILL-1). Pressing a control in the overlay never pans.
  - The cursor shows "grab" while zoomed and "grabbing" while dragging; it still hides when idle (CELL-4).
- **ZOOM-2** A "100%" control and double-click with a modifier reset the zoom. Zoom resets when you leave filled mode, and when a filled multi-camera cell steps to another camera (CELL-3).
  - The "100%" control is an icon button (a magnifier with a minus, tooltip "Reset zoom to 100%…") in the overlay's strip (CELL-3), shown whenever the cell is filled and **disabled at 1×**, where it would do nothing (the user's call, 2026-11-16; it used to be a "100%" text button shown only while zoomed).
  - The double-click is a primary-button double-click with Ctrl, Cmd, Alt or Shift held; it never leaves fill (FILL-1). On macOS Ctrl+click is a context click, so Ctrl + double-click does not reset there; the "100%" control's tooltip names the modifiers that work on the platform (⌘/⌥/⇧ on macOS, Ctrl/Alt/Shift elsewhere).
  - Every way out of fill resets the zoom: `Esc`, the back control, a plain double-click, a View switch, or the filled cell going away. Filling the camera again starts at 1×.
- **ZOOM-3** Zoom is a client-side CSS transform. It never changes camera settings.
  - The transform is on the player only: the overlay (name, badge, controls) stays the same size and in place while the picture zooms. The stream and its quality are untouched, and the player is the same one before, during and after zooming (FILL-2).

### Audio (AUD)
- **AUD-1** Every cell starts muted. The audio control only shows when `featureFlags.hasMic && isMicEnabled`.
  - The control is a mute toggle in the cell's strip (CELL-3), in the grid and in fill: a speaker crossed out while muted, with sound waves (and the accent colour) while heard; its tooltip says what a press does. A camera whose mic is missing or switched off has none, and neither does a camera that is offline or connecting (CAM-3; user decision, 2026-11-16): the toggle shows only while the camera is connected. Neither does a package-channel cell (CAM-4): the mic flags are the doorbell's main camera's, and whether the package stream carries audio is unverified, so the doorbell is heard from its own cell (P5.1).
- **AUD-2** Unmuting a cell mutes all other cells. Only one source plays at a time.
  - The one source heard is a cell of the View on screen **with the camera it showed when it was unmuted** (P5.1). Audio never follows a cell onto another camera (user decision, 2026-11-16): if the unmuted cell's visible camera changes for any reason — a timed rotation, a manual next/previous, a motion or ring trigger switch — or the camera goes missing (CAM-2), goes offline or reconnecting (CAM-3), or its mic is switched off, the cell is muted, and it stays muted if the camera comes back. Switching View, leaving the Live screen (or opening the View editor) and the cell disappearing all leave nothing audible. A hidden player — the pre-warm of the next rotation camera (CELL-2) or the incoming layer of a quality swap (QUAL-6) — is always muted.
  - **Filling a cell mutes every other cell** (user decision, 2026-11-16). The covered cells' controls can't be reached, so only what is on screen is heard; the filled cell keeps its audio, and a cell muted by a fill stays muted after leaving it.
- **AUD-3** Volume control in filled mode. A global mute-all shortcut (`M`).
  - **Volume** (user decision, 2026-11-16): one level for the whole app, **for the session only** (not saved in the config), at 100% on every launch. A compact slider in the strip shows it, only while filled and only on a cell whose camera has audio (AUD-1). It applies to whatever plays (only the one source can), whether or not the filled cell is the one heard; moving it never unmutes, and muting keeps it. After a drag with the pointer the slider hands the focus back, so `Esc`, `1`–`9` and `M` work again at once; keyboard focus stays and the arrows move it.
  - **`M` mutes everything; it is not a toggle** (user decision, 2026-11-16). With nothing unmuted it does nothing. Only on the Live screen, and — like fill's `Esc` and the View shortcuts — not while typing in an input, select, textarea or contentEditable, not with Ctrl/Cmd/Alt held (Shift is fine), and not on key repeat.

### Access door unlock (DOOR)
- **DOOR-0** Access integration is an **optional feature, disabled by default**. Settings has an "Enable UniFi Access" switch. While it's off, the app makes **no Access API calls**, doesn't ask for or store an Access token, and hides everything door-related: the Doors button and screen (DOOR-7, which holds the door links, DOOR-2), the unlock controls and the door list in Test connection. Turning it on reveals the token field and those controls. Turning it off again keeps the saved token, door links and polling settings (DOOR-9) (so they come back when re-enabled), but the app stops using them. A setting in Settings can also point the Access client at a different base URL (used for the dev mock, §5.2).
  - **Doors button** (P5.6). The header nav has a "Doors" button, between "Cameras" and "Live", only while the **saved** Access switch is on; the unsaved checkbox in Settings reveals nothing that calls Access. With the switch off there is no button and no screen, so nothing asks main to read the doors. If the switch is saved off while the Doors screen is showing, the app moves to Settings (where the switch is), and leaving the screen is what tells main to stop reading. Doors is never the start screen (CON-4): opening it makes main read the Access console, which only the user asks for.
- **DOOR-1** When Access is enabled and a token is set, the app fetches the list of doors (`GET /doors`, §5.2). Since P5.6 the list the user sees is read by main's door-state monitor (DOOR-6) **while the Doors screen is open**, and reaches the renderer inside the `doorsScreen` state (DOOR-7, §6.1): once when the screen opens, then at DOOR-6's cadence, and from scratch on the screen's Refresh. Main keeps that list only while the screen is open and the reading runs, and drops it and reads again when the console block is saved, the Access token is saved or cleared, or a certificate is accepted (its door ids may belong to another console or account). While Access is off the read is not made at all (DOOR-0). The reads move the Access status as DOOR-6 says. A list that cannot be read is shown on the screen with its message, plus where to fix it for the cases Settings can fix: accept the Access certificate (`pin-required`), check a changed one (`pin-mismatch`), save a valid Access token (`auth`), save a console address (`not-configured`), turn Access on (`disabled`).
  - **There is no one-shot door list call** (user decision 2026-11-18). P5.3's `vp:doors/list` — Settings' Door links card read the list once per visit through it, never on a timer — went with that card: P5.6 removed the channel, its handler and the manager call behind it, since no screen sent it. The Doors screen's state is the only way the door list reaches the renderer. Test connection still counts the doors with its own `GET /doors` (CON-4).
- **DOOR-2** The user links a camera to a door. In the prototype this mapping is manual. Later the app could suggest matches by name or device.
  - **On the door cards** (P5.6, user decision 2026-11-18; moved from Settings' Door links card of P5.3, whose rules below still hold unless said otherwise). Each door card of the Doors screen (DOOR-7) has a **Cameras** section: the cameras linked to that door, each a chip with its unlink button (nothing when there are none; user decision 2026-11-19), and an Add camera control. The persisted model is camera → door (`doorLinks`), so a camera belongs to at most one door and several cameras may share a door; **moving a camera between doors is unlink, then add** (user decision 2026-11-17: Add camera lists unlinked cameras only). A doorbell's package channel (CAM-4) is not an entry of its own: it **shares the doorbell's link**, and the unlock control on a package cell uses that link (DOOR-3). A door with **no hub** has no Add camera control (user decision 2026-11-19: nothing on its card would have an effect); cameras linked to it earlier stay listed there so they can be unlinked, and main still accepts such a link.
  - **Add camera is a dropdown plus an Add button** (user decision 2026-11-17): the dropdown only holds a pending choice under a placeholder, since an arrow key on a closed select fires `change` on Windows and Linux; Add is usable only with something chosen and no save running, acts on the choice, and resets the dropdown. Its accessible name is "Add camera to <door>"; the dropdown has its own label. It lists only the inventory cameras linked to no door, in camera-list order; the placeholder reads "Add camera…", "No unlinked cameras", or "Cameras not loaded yet" while the inventory is empty.
  - **Every listed door has a card, linked or not** (P5.6), so P5.3's Add door picker, its session-only empty cards and Remove door are gone: a door with no camera is just a card with an empty camera list, nothing is stored for it, and a door's cameras are unlinked one at a time. Each linked camera is a row with a ✕ ("Unlink <camera> from <door>") that unlinks it. Cameras inside a card are in camera-list order, then unknown or not-loaded ones by id.
  - Every change **saves at once, with no confirm dialog** (as in P5.3; coordinator decision 2026-11-18: a link changes no door, so DOOR-7's confirmation does not apply). One save at a time for the whole screen, each built from the links as stored at that moment; controls stay focusable while a save runs (marked unavailable rather than disabled), and a ✕ that removes the row holding the focus hands it to the card's Add camera dropdown, else to Refresh. A failed save keeps the stored links and shows why on the door's card, as a status line.
  - **Links are never pruned automatically.** A linked door the loaded list does not have keeps a card as "Unknown door (<id>)", after the listed doors, by id; while there is no list (still loading, or the read failed) linked doors show as "Door <id>" cards. Such a card shows the state "Unknown" and has no actions and no Add camera: its cameras can be unlinked, and that is all. A linked camera not in a non-empty inventory shows as "Unknown camera (<id>)"; with an empty inventory (not connected yet) as "Camera <id> — not loaded yet", under a "Connect to the console to link cameras to doors" notice.
  - Saving is `vp:doors/links` with the **whole map** (§6.1), persisted to `config.json` `doorLinks`. It makes no Access call and is accepted whether Access is on or off, since the links are kept while it is off (DOOR-0).
- **DOOR-3** The cell or filled-view unlock control asks for confirmation (press-and-hold for 1 s, or a confirm dialog). It then calls the Access remote-unlock endpoint and shows success or failure. Since P5.6 the same rule covers every request that changes a door — unlock, lock and the lock rules from the Doors screen (DOOR-7), lockdown and evacuation (DOOR-8): one confirmed user action is exactly one request, never retried.
  - **Two ways of confirming** (user decision 2026-11-18). A cell's unlock button is the 1 s pointer hold below, with no dialog. On the Doors screen **every action is confirmed in a dialog, unlock included, and there is no press-and-hold** (DOOR-7).
  - **Unlock button** (P5.4, user decisions 2026-11-18). A rounded-rectangle (`--radius`), icon-only door button, 41 px square (larger than the strip's 28 px chips; user request 2026-11-18), at the **bottom centre** of the cell, in the grid and in fill, with a tooltip and an accessible name. It shows only while Access is **saved** as on (DOOR-0), the cell's camera has a door link (a package-channel cell uses the doorbell's link, DOOR-2) and the camera is **connected and streaming**; never on a missing-camera placeholder. It is **always visible** while drawn, in the grid and in fill: it does not auto-hide with the controls strip (CELL-4; user decision 2026-11-18). Pressing it is only the button's: it never fills the cell, pans a zoom or counts towards a double-click (FILL-1, ZOOM-1).
  - **Press and hold for 1 s, pointer only.** A mouse, touch or pen hold of the primary button for 1 s sends one unlock; releasing, leaving the button or a cancelled pointer before then sends nothing. Keyboard activation (Space, Enter, a synthetic click) never unlocks (DOOR-4, strict reading). A fill grows over the hold (`transform` only; a static "holding" style under reduced motion, still 1 s). While the unlock is in flight the button is busy and ignores presses.
  - **Colour.** The button shows the door's real lock state (DOOR-6): green with the open-door icon while the door's lock relay reads `unlock`, whoever unlocked it, and neutral with the closed-door icon while it reads `lock` **or is not known**. P5.4's stand-in (green for 5 s after the app's own unlock) is gone (P5.5). Holding the button while the door is already unlocked sends another unlock.
  - **Result.** A toast (`ui/Toast`, bottom right of the window so it never covers the button): "Door unlocked for <camera>." on success (auto-dismissed), "Couldn't unlock the door for <camera>. <reason>" on failure (stays until dismissed or ~10 s). The door is named by its camera, since the Live screen does not read the door list (user decision 2026-11-18: no extra Access call for the door's name). A failed unlock is never retried by the app; the user holds again. **Outcome unknown** (user decision 2026-11-18): when the request may have reached the console but no answer came back (a timeout, or the connection lost after connecting), the door may have opened, so the app does not say it failed: the button goes back to neutral and a warning toast reads "No answer from Access. The door for <camera> may have unlocked — check before trying again."
- **DOOR-4** Unlock never runs from a keyboard shortcut alone or from an automatic trigger, and since P5.6 neither does any other request that changes a door (lock, a lock rule, lockdown, evacuation): no timer, no pushed state and no retry sends one.
  - **From a cell** the renderer never sends a door id: it names the cell's camera, and main resolves the door from the saved links (P5.4). Unchanged by P5.6.
  - **From the Doors screen** (amended in P5.6, coordinator decision 2026-11-18) the renderer names a **door id**, because a door with no linked camera has nothing else to be named by. Main acts on it only if the id is in the door list **main itself last read from the current Access endpoint while the Doors screen is open** (DOOR-1). Any other id — never read, read before the console, token or certificate changed (a read still in flight at that moment included: its answer is not taken), sent with the screen closed or with the reading stopped — is answered `not-found` with **no Access call**. The id is compared with the list, never interpreted. **A stale list is refused too** (user decision 2026-11-18, defence in depth): once two door reads in a row have failed — the condition that makes DOOR-7 draw the list as stale — main still holds the list, but answers every door action `unavailable` with **no Access call** ("The door's state is not known right now, so nothing was sent. Try again once the doors can be read."), whatever the screen's disabled buttons do. One failed read does not: the list is still the last good one.
  - On the Doors screen a key can activate a button, but a button only opens the confirm dialog; the request is sent from the dialog's confirm button (DOOR-7).
- **DOOR-6** (P5.5, user request 2026-11-18; extended in P5.6) The unlock button shows the linked door's **real lock state at all times**, including unlocks and relocks made elsewhere (a card or PIN at the reader, the Access app, an unlock schedule, a lock rule). Since P5.6 the Doors screen's cards show every door's state from the same reads (DOOR-7).
  - **Source of truth.** `GET /doors` (§5.2), read by main; the button follows `door_lock_relay_status`. The Access notifications WebSocket is used only as a hint to read sooner: the official reference documents no relock event and no event that carries the relay state, and does not say whether unlocks other than an admin's remote unlock are pushed.
  - **Only while it is needed.** Main watches only while Access is saved as on, the Access address resolves, a token is stored, and at least one of **two watchers** wants it (P5.6): the Live screen showing a View in which at least one camera has a door link (with at least one link saved), or the Doors screen being open, which needs no link. Otherwise there is no socket and no polling, and while Access is off no Access call of any kind (DOOR-0). The two are independent and served by the same reads: one `GET /doors` loop and one socket, whoever is watching. For the Live screen main tracks the linked doors; while the Doors screen is open it tracks **every** door the console lists, so the unlocked cadence below follows any of them, and it goes back to the linked ones when the screen closes.
  - **Cadence.** One read when watching starts, and one at once when the Doors screen opens while the Live screen was already being watched; the notifications socket is opened once that read has worked, so it is never tried with a token or certificate the console has not accepted. Then a read every 5 s while the socket is open, and every 2 s for the first 60 s that it is not; after that 5 s again, with one log line saying door state is running on polling only (a token without `view:device`, or a console without the socket). A read is made at once (coalesced, at most one in flight) after the app's own unlock, door action or emergency change answers, on any notification frame, and when the socket (re)opens. While any watched door reads `unlock`, and for 3 s after such a trigger, reads are 1 s apart so the relock shows promptly; a door that stays unlocked for more than 30 s (held by a lock rule or a schedule) drops back to the normal cadence. The 5 s, 2 s and 1 s are the defaults of three settings since P5.6 (DOOR-9); the 60 s, 3 s and 30 s windows are fixed. The unlocked interval never makes reads slower than the 5 s / 2 s one in force: the shorter of the two is used.
  - **Unknown is never shown as a state.** A door the last read did not return, or any door after two failed reads in a row, is unknown and drawn neutral. Failed reads back off (doubling to 30 s), and are never closer together than the read interval in force: with DOOR-9's interval set above 30 s, a console that is not answering is read at that interval, not more often than a healthy one. A certificate that is not accepted, Access switched off, or the console refusing the whole API (`CODE_OTHERS_UID_ADOPTED_NOT_SUPPORTED`, Identity Enterprise) stops the watching until the setting changes or the Live screen or the Doors screen is opened again. A rejected token stops it too, but is tried again every 60 s with a single read, and any other Access call that succeeds (an unlock, a Doors screen action, Test connection) restarts it at once, so a wall display recovers from a console restart without anyone touching it. If the Live screen's request to start watching fails (main still starting), it asks again after 2 s, then every 5 s; the Doors screen's request does the same.
  - **Read only.** Watching never unlocks, locks or changes anything on the console (DOOR-3/4). The Access status (CON-5) follows these reads, changing only on a transition: to `error` on the second failed read in a row (or at once on a failure that stops the watching), back to `connected` on the next answer. Routine reads are not logged one line each. The Doors screen's lock-rule and emergency reads (DOOR-7) are read-only as well, and their failures never move the Access status.
- **DOOR-5** Each unlock (time, door, result) goes to a local log file. Since P5.6 so does every other door action and every emergency change (coordinator decision 2026-11-18): each changes a physical door just as an unlock does.
  - `<userData>/logs/unlock.log` (P5.4; extended in P5.6, the file keeps its name), JSON Lines, one line per attempt that reaches a handler in main — those refused there before sending included: for a cell's unlock, Access off, no link, no token, certificate not accepted; for a Doors screen action, Access off, a door id main has not read (DOOR-4), a stale door list (DOOR-4), a door with no hub; for an emergency change, Access off. An attempt refused by the IPC layer before that (the app still starting, or a malformed payload — lockdown and evacuation both on is one) is not logged and sends nothing to Access (user decision 2026-11-18).
  - A line is `{ time, action, cameraRef, cameraName, doorId, doorName, minutes, lockdown, evacuation, result: "success" | "failure" | "unknown", errorKind, message }`, every key always present and in this order, with `time` in ISO 8601 UTC and `errorKind` / `message` `null` on success and set for `failure` and `unknown`. `action` is what was **sent** — `unlock` (the only value a cell produces), or the lock rule's type: `lock_now`, `reset`, `keep_lock`, `keep_unlock`, `custom` — or, for an attempt refused before anything was sent, what was **asked**, which adds `lock` (nothing was sent for it); or `emergency`. `cameraRef` / `cameraName` are set for a cell's unlock and `null` for the Doors screen. `doorId` is the linked door, or the id the Doors screen named **as received** (also when main refused it), and `null` for `emergency`. `doorName` is the door's name from the list main read, for a Doors screen action on a door main knows; `null` otherwise, the cell path included (P5.4: no extra read for the name). `minutes` is a `custom` rule's duration; `lockdown` / `evacuation` are the flags an `emergency` line asked for; each is `null` on every other line. A line written before P5.6 has only `time, cameraRef, cameraName, doorId, result, errorKind, message` — the same keys in the same relative order — and is a cell's unlock.
  - The message is the same safe text the toast shows, never a token or a URL with a credential. Above 1 MiB the file is renamed to `unlock.log.1` (replacing an older one) before the next line. A failed write is reported in main's console and never changes the action's result. Main's console line for a Doors screen attempt names a door id only when main has read that door itself.
- **DOOR-7** (P5.6, user request 2026-11-18) **Doors screen.** While Access is saved as on (DOOR-0) a Doors screen lists **every** Access door, linked to a camera or not, with its live state, what is controlling it, its actions and its linked cameras.
  - **Layout** (user decision 2026-11-18). **Door cards**: one card per Access door with everything about that door on it, flowing horizontally and wrapping, down to one column at narrow widths. The screen header holds the title, the Lockdown and Evacuation buttons (DOOR-8) and Refresh; the Polling card (DOOR-9), titled **Settings** with a gear icon, is a collapsible bar pinned to the bottom of the screen, closed by default, that opens upwards (user decision 2026-11-19). The cards of a row are all as tall as the tallest. Listed doors are in name order (`full_name`, falling back to `name`, then the id), then linked doors the list lacks, by id (DOOR-2).
  - **A card** (layout: user decisions 2026-11-19) shows, top to bottom: the door's name, with room for two lines always kept (a longer name is cut there) so the controls line up across a row of cards; at its top right, the lock state as a padlock alone — an open padlock in green while `door_lock_relay_status` reads `unlock`, a closed one in the warning amber while it reads `lock`, each named "Unlocked" / "Locked" in its tooltip and for assistive tech — or the muted word "Unknown" when it is not known; the Unlock and Lock buttons; a "Set a rule…" dropdown with Apply, and the rule line under it; and the Cameras section (DOOR-2). The door position sensor is **not shown** (user decision 2026-11-19). State is live through DOOR-6's reads, which watch every door while this screen is open.
  - **Where it comes from.** Main reads the console while the screen is open and pushes one whole `doorsScreen` state: the door list, whether it is stale, each door's rule, the emergency status, and why the list cannot be read (§6.1). The renderer reads nothing itself and draws only that.
  - **Rule line.** What is controlling the door, from `GET /doors/{id}/lock_rule`: "On an unlock schedule" (`schedule`), "Kept unlocked" (`keep_unlock`), "Kept locked" (`keep_lock`), "Unlocked until …" or "Unlocked for a set time" (`custom`), "Locked early, ahead of its unlock schedule" (`lock_early`), and "Rule: <type>" for a type the reference does not list. " until <time>" is added when the rule's `ended_time` is in the future: the locale's short time, with the date when that is not today and the year when it is not this year; an absent, zero or past end time adds nothing. No line for a door with no rule (`type: ""`) or one whose rule is not known (not read yet, the read failed, or a console older than Access 1.24.6, which has no such endpoint).
  - **Rule type and end time are all there is** (PDF check, 2026-11-18, the task's item 3). The official document gives **no name and no hours for a door's unlock schedule**: `GET /doors/{id}/lock_rule` answers only `type` and `ended_time`, and the schedules of the PDF's §5 are access-policy schedules, not a door's unlock schedule. So the card cannot say which schedule, or when it runs again.
  - **Details reads** (coordinator decision 2026-11-18). The lock rules and the emergency status (DOOR-8) are read **only while the Doors screen is open**, in rounds: one `GET /doors/settings/emergency`, then one `GET /doors/{id}/lock_rule` per door, **one request after the other**, never in parallel, at most one round in flight, and any number of requests for a round while one runs make exactly one more. A **full** round (the emergency status and every door) runs once the first door read has worked, then every `detailsSec` (DOOR-9, default 30 s), and at once after the app's own emergency change answers, when the list gains or loses a door, and when the door reads work again after failing. In between, a round reads **only what its reason touched**: after the app's own door action answers, that door's rule and the emergency status; when a door's relay changes, the rule of each door whose relay changed and the emergency status, so a lockdown or evacuation started elsewhere shows its banner at once. Requests waiting for the same round are merged (a full one wins), a door that is no longer listed is never asked about, and a partial round does not postpone the next timed full one. A failed read means "unknown" for that rule or status and nothing more: it is not retried before the next round, never moves the Access status, and is logged when reading starts or stops working, not per request. A failure that is about the endpoint rather than one door (no answer, a rejected token, a certificate) ends the round, with the rest counted as unknown; timed rounds are skipped while the door reads themselves are failing.
  - **Actions.** Unlock (`PUT /doors/{id}/unlock`, momentary, as from a cell). Lock, which is **always** the lock rule `lock_now` (user decision 2026-11-18): the reference says it "terminates both the unlock schedule and any temporary unlock at once", so it locks the door whatever is holding it unlocked. Main does not choose `reset` or `lock_early` from the door's rule as it last read it: that rule can be out of date, and `reset` on a door that has since gone onto its unlock schedule would silently do nothing. The app never sends `lock_early`. What `lock_now` does to the rest of the day's unlock schedule on real hardware is not documented and is for OS-1 (R3). The dropdown offers the temporary rules: "Keep unlocked" (`keep_unlock`), "Keep locked" (`keep_lock`), "Unlock for a set time" (`custom`, with a minutes field: whole minutes, 1 to 1440, starting at 15, validated under the field) and "Back to normal" (`reset`), the last only while the door's rule reads `keep_lock`, `keep_unlock` or `custom`. All but Unlock are `PUT /doors/{id}/lock_rule`.
  - **Every action is confirmed in a dialog** (user decision 2026-11-18): unlock included, with **no press-and-hold on this screen**. A button, or Apply, only opens a `ConfirmDialog` whose title names the door and the action ("Unlock Front Door?") and whose confirm button names the action alone ("Unlock", "Keep unlocked", "Unlock for 15 minutes"; user decision 2026-11-19: the title already has the door), with one sentence saying what happens. Confirming sends exactly one `vp:doors/action`; cancelling sends nothing. The dropdown only holds a pending choice — nothing acts on `change` (as DOOR-2's Add camera) — and returns to its placeholder once an action was sent. One action at a time per door: while it is in flight the card's controls are busy and ignore presses.
  - **When a door cannot be acted on.** A door with **no hub** (`is_bind_hub: false`): its card is the name and the line "No door hub, so it can't be unlocked or locked from here." — **no lock state** (what the console reports as the relay of a door with no hub says nothing about a lock, so it is not shown as Locked, or as Unlocked during an evacuation), no buttons, no rule control and no Add camera (user decisions 2026-11-19). Main refuses every action on such a door as well (`bad-request`, no Access call; coordinator decision 2026-11-18), rather than relaying the console's refusal. A door whose state is not known right now (stale, below): controls disabled, "This door's state is not known right now.", and main refuses the action as well (`unavailable`, no Access call; DOOR-4). A card for a door the list does not have has no actions at all (DOOR-2).
  - **Result.** A toast, as for a cell's unlock (DOOR-3): success, auto-dismissed ("Front Door unlocked.", "Front Door locked.", "Front Door will stay unlocked.", "Front Door unlocked for 15 minutes.", "Front Door is back to normal."); failure, "Couldn't unlock Front Door. <reason>", never retried by the app; and **outcome unknown** — the request may have reached the console but no answer came back — a warning, "No answer from Access. Front Door may have unlocked — check before trying again." The door's new state is not taken from the answer: main reads the doors and the details at once after it, and the card follows the next push.
  - **Unknown is never shown as a state.** Once two door reads in a row have failed the list is **stale**: the cards and their names stay, every lock state reads "Unknown", the rule lines go, the emergency status is unknown, the actions are disabled (and refused by main, DOOR-4), and a warning banner above the cards reads "The doors cannot be read right now, so their states are not known. <reason>". The next read that works restores all of it. **One failed read shows nothing** (user decision 2026-11-18): with a list on screen, main reports a failing read only together with `stale`, from the second failure in a row, so a single lost poll neither warns nor changes a card.
  - **Screen states.** No list and no reason yet: a spinner, "Reading the doors…". No list and a reason (Access not usable, a rejected token or certificate, a failed first read): "The doors could not be read", the message, where to fix it (DOOR-1), **Open settings** when Settings can fix it, and **Try again**; linked doors still get their cards underneath (DOOR-2). A list with no doors: "No doors — Your console has no doors. Add one in Access, then press Refresh." Otherwise the cards. With an empty camera inventory a muted line says to connect to the console to link cameras.
  - **Refresh** (and Try again) closes the screen's watch and opens it again: main forgets the list, the rules and the emergency status and reads everything from scratch, and the screen shows its loading state in between. There is no separate "read now" call. Refresh is disabled while loading.
  - **Decided in review (2026-11-18).** (1) Lock always sends `lock_now`, never a rule chosen from main's last read of the door's rule (user decision; Actions above). (2) Main refuses a door action while its list is stale — `unavailable`, no Access call, a line in `unlock.log` — in addition to the screen's disabled buttons (user decision; DOOR-4). (3) The read-failure warning appears together with the stale state, from the second failed read in a row; a single failed read shows nothing (user decision; above). (4) `vp:doors/emergency` (DOOR-8) is accepted with the Doors screen closed and while the list is stale: it names no door, so there is no door id to check against a list, and lockdown and evacuation must not depend on which screen is showing or on a read that happens to be failing (coordinator decision).
- **DOOR-8** (P5.6, user request 2026-11-18) **Emergency: lockdown and evacuation.** The Doors screen shows and sets the emergency status of **all** doors: lockdown keeps every door locked, evacuation keeps every door unlocked.
  - **Read** from `GET /doors/settings/emergency` in DOOR-7's details rounds, so only while the Doors screen is open; unknown until a read works, after a failed one, and on a console older than Access 1.24.6. Nothing outside the Doors screen reads or shows it.
  - **Lockdown and Evacuation buttons in the screen header** (user decision 2026-11-18), in the danger style. A button is disabled, with the reason in its tooltip, while the status is not known, while its own mode is already on, and while the other mode is on ("Lockdown is on. End it before starting evacuation.").
  - **Banner while one is on**: an error-kind banner at the top of the screen, "Lockdown is on. Every door is kept locked." or "Evacuation is on. Every door is kept unlocked.", with an **End lockdown** / **End evacuation** button.
  - **Every start and every end goes through a `ConfirmDialog` that says it applies to every door** ("Start evacuation?" — "This applies to every door. All doors are unlocked and stay unlocked until you end the evacuation."), with the action named on the confirm button and the destructive style for a start. Confirming sends exactly one `vp:doors/emergency`, which is one `PUT /doors/settings/emergency`, never retried (DOOR-3/4).
  - **The pair is computed after the dialog, from the status known at that moment.** If it is unknown by then, or a start is no longer allowed because a mode has come on meanwhile, nothing is sent and a toast says so. Starting a mode sends it `true` and the other `false`; ending one sends it `false` and leaves the other as the console last reported it.
  - **Lockdown and evacuation cannot both be requested** (coordinator decision 2026-11-18): the reference does not say what both would mean and no dialog offers it. The IPC schema refuses the payload (`invalid-request`, nothing sent), and main repeats the check before the PUT (`bad-request`).
  - **Result.** A toast: "Lockdown is on. Every door is kept locked.", "Evacuation is on. Every door is unlocked.", "Lockdown ended."; "Couldn't start lockdown. <reason>" on failure; and for an unknown outcome a warning, "No answer from Access. Lockdown may have started — check the banner before trying again." Main reads the doors and a full details round at once after the answer, so the banner and every card follow. Each attempt is a line in `unlock.log` (DOOR-5).
- **DOOR-9** (P5.6, user request 2026-11-18) **Polling settings.** How often main reads the Access door API is a persisted setting, `accessPolling` (§6), edited on the Doors screen's Polling card, which is titled **Settings** on screen (user decision 2026-11-19).
  - **Four intervals, in whole seconds** (coordinator decision 2026-11-18), the first three being the values P5.5 hard-coded: `withSocketSec` — door states while the notifications socket is open, and once it has been down for more than a minute — default **5**, range **2–60**; `withoutSocketSec` — door states for the first minute the socket is not open — default **2**, range **1–30**; `unlockedSec` — door states while a watched door is unlocked and just after a trigger — default **1**, range **1–10**; `detailsSec` — the lock rules and the emergency status (DOOR-7) — default **30**, range **10–600**. DOOR-6's other timings (the 60 s, 3 s and 30 s windows, the failure back-off, the 60 s retry of a rejected token) are not settings.
  - **Why bounded.** The floors keep a setting from turning the app into a request flood against a console whose rate limit is undocumented (§5.2); the ceilings keep a door's state from going stale for longer than a person would wait. The ranges overlap, and an `unlockedSec` above the baseline in force is not used (DOOR-6).
  - **The card is collapsible** (user decision 2026-11-19): closed by default, a bar at the bottom of the Doors screen with the title and a chevron; opening it grows the card upwards, over the door cards if need be. What was typed is kept while it is closed, as long as the screen stays open.
  - **The card is a form**, unlike the rest of the screen: four number fields in a column (user decisions 2026-11-19), each row a label, the input and, to its right, the range and one short line of help ("2 to 60 seconds. Access reports changes itself; this is a backup check."). The three door-state intervals are one group titled **Lock states** — "With Access notifications", "Without Access notifications", "While a door is unlocked" — and the fourth is its own group, **Rules and emergency status**. Nothing is saved while typing; an invalid field says "Enter a whole number from 2 to 60." in place of its help; **Save** is available only with every field valid and at least one changed; **Reset to defaults** fills the fields and still needs Save. The outcome is a status line: "Saved. The new intervals are in use."
  - **Main validates** (`vp:doors/polling`, §6.1): all four values, whole numbers inside their ranges, or the save is refused; the form's own check only saves the round trip. Saving makes no Access call and is accepted while Access is off (the values are kept and unused, DOOR-0).
  - **Applied without a restart.** The monitor reads the intervals at every scheduling decision and re-arms its pending timers on a save, so a shorter interval takes effect at once rather than after the old one runs out.
  - **A persisted value that is out of range falls back to the default**, as does a missing or non-integer one: that field loads as its default — not clamped to the nearest bound, so a typo lands on a value somebody chose — and a block that is not an object loads as all four defaults. One bad interval costs that setting, not the config file. No `schemaVersion` bump: a file written before P5.6 loads with P5.5's intervals (§6).

### 5.1 UniFi Protect Integration API (official contract, verified against the console in P0.3)

**Source of truth:** the official Ubiquiti contract, vendored at `docs/reference/protect-openapi-v7.3.74.json` (endpoint index: `docs/reference/protect-endpoints-v7.3.74.md`). It was fetched from `developer.ui.com/protect/v7.3.74/`. This matches the console exactly. (The 7.3.74 contract is byte-identical to 7.3.70.) The latest published docs are v7.4.96. When Protect is upgraded, re-download the matching version, regenerate the types and diff the contract. **Generate TypeScript types from this file (openapi-typescript). Don't write them by hand.**

**Verified on the console (P0.3, 2026-11-12, `docs/spikes/P0.3-protect-api.md`):** `GET /v1/meta/info` returned `applicationVersion: "7.3.74"`, matching the vendored contract. Every response sample validated against the contract except for the two drift items noted below. Three WebSocket runs totalling 9 minutes captured 70 event messages, all `smartDetectZone`; a later 5-minute re-run, after motion detection was enabled on two cameras, captured the 6 `motion` events. Every captured message validated against the contract.

- **Base URL (local):** `https://<consoleIP>/proxy/protect/integration` + `/v1/...`
- **Base URL (cloud, not used in prototype):** `https://api.ui.com/v1/connector/consoles/{consoleId}/proxy/protect/integration`. This is the Site Manager Cloud Connector. It carries REST and control calls without a VPN, **but the RTSPS URLs it returns still point at the console**, so live video still needs the LAN or a VPN. Possible MVP use: remote status and door unlock without a VPN.
- **Auth:** header `X-API-KEY: <key>`. The official docs say to generate keys at unifi.ui.com, but **a key created locally in UniFi OS → Settings → Control Plane → Integrations works on the local endpoint** (P0.3 §1, R6 resolved); no unifi.ui.com key is needed. The same header authenticates both WebSockets (`wss://<console>/proxy/protect/integration/v1/subscribe/{devices,events}`), with no subprotocol and no extensions. There is no read-only scope, so treat the key as an admin credential. **Unverified:** no run has pointed a *wrong* key at the two WebSockets, and undici fails a non-101 handshake without exposing the HTTP response, so what a rejected upgrade looks like to the client is unknown. P1.3 looks for 401/403 in the error's `cause` chain and then in its message, stops retrying when it finds one (a reconnect loop cannot fix a bad key) and treats anything unrecognised as a retryable network error. Confirm it on the next console run.
- **Errors:** every endpoint returns `{ error: string, name: string, cause?: object }` for non-2xx responses. Map these into typed app errors.
- **TLS (CON-3):** the console presents a self-signed leaf certificate, so the pinned undici Agent **must disable TLS session resumption** (`maxCachedSessions: 0`) or handle resumed sessions explicitly. On a resumed session `getPeerCertificate()` returns no fingerprint and the pin check fails (P0.3 §8). P1.2 has to carry this.

**Rate limit (not in the contract, found in P0.3 §7)**

- **10 requests per 1-second window, per key.** Over the limit: `429 { error: "Too many requests", name: "TOO_MANY_REQUESTS_ERROR", windowMs: 1000, limit: 10 }`. Treat 429 as retryable after `windowMs` — **for a GET**. A rate-limited **POST is never retried automatically** (P0.3's spike rule, which P1.3's client follows): `POST rtsps-stream` creates state, so the caller re-reads with a GET and decides whether the POST is still needed. The retry budget is 4 attempts.
- Responses carry `ratelimit: "10-in-1sec"; r=<remaining>; t=<reset s>` and `ratelimit-policy: "10-in-1sec"; q=10; w=1; pk=:<partition key>:`. The `pk` value is an opaque per-client key: **never log it.** Log these headers through an allowlist of the policy name and the numeric parameters only.
- **WebSocket upgrades count against the same budget.** A rate-limited upgrade is accepted, sent one JSON text frame with the 429 body, then closed with code **4500** and reason `Too many requests`.
- Consequence for P1.7 and P2.2: fetching snapshots for 15 cameras, or `ensureStream` for a 10-cell View, will blow the limit unless the calls are queued or throttled (the spikes spaced them ≥ 150 ms apart), and WebSocket reconnects must back off.

**Event lifecycle (verified in P0.3 §5)**

- An event **starts** with `add`, whose item **omits `end` entirely** — it is not `end: null`. It **ends** with an `update` that sets `end`. `update` items are **full** event objects (`id, modelKey, type, start, device, smartDetectTypes[, end]`), not partial patches.
- **End updates may repeat.** The smartDetect end update was repeated two or three times with identical payloads 0–0.5 s apart; the motion end update arrived once. Consumers must be idempotent on `(id, end)`.
- **End signals lag the real world.** One smartDetect `end` update arrived about 4 s after its `end` timestamp, so expect an end signal 3–5 s after the scene goes quiet. Motion events ran roughly 10–30 s per walk-by. P0.3's two motion figures — a 16.6 s `start`→`end` and an end update 9.3 s after the `add` — come from different events and can't be combined, so **motion's end-update lag is unmeasured**; P4.1 must not depend on it. CELL-2's `motionHoldSec` is measured from the `end` timestamp, not from arrival.
- **Keepalive:** the server sent **no WebSocket pings** in 9 minutes and did not close an idle socket. The client has to detect dead connections itself (NFR-7). **P1.3 does not send pings:** undici's `WebSocket` has no standard ping API, and its connector already turns TCP keepalive on (60 s idle), so a dead peer surfaces as a socket error and the subscription reconnects with backoff. An app-level idle timeout exists but is **off by default** — both feeds are legitimately silent for many minutes, so a timeout would mostly cause reconnects that each spend a rate-limit permit and a re-read of `GET /v1/cameras`.

### 5.2 UniFi Access API

> **Official contract, not yet run against hardware.** Ubiquiti's developer portal does not cover Access, but the console itself ships the API document (Access > Settings > General > Advanced > API Token > Download API documentation). It is vendored as `docs/reference/access-api-reference-v4.2.16.pdf`, with the parts the app uses extracted to `docs/reference/access-endpoints-v4.2.16.md`. Until P5.5 this section was built from community sources. The development network has no Access, so **OS-1 is still what confirms the console behaves as documented.**

- Base: `https://<console>:12445/api/v1/developer`, HTTPS with a self-generated certificate. In the app this whole URL is `console.accessBaseUrl` (§6), so the dev mock or another path needs no code change — only the setting.
- Auth: `Authorization: Bearer <token>`, on REST and on the WebSocket upgrade. The token is created in Access > Settings > General > Advanced > API Token and needs the scopes `view:space` (read doors, lock rules and the emergency status), `edit:space` (unlock, set a lock rule, set the emergency status) and `view:device` (notifications).
- **Used by the app:** `GET /doors` (the Doors screen's door list, DOOR-1/7; live lock state, DOOR-6), `PUT /doors/{id}/unlock` (DOOR-3, from a cell and from the Doors screen), `GET /doors/{id}/lock_rule` and `GET /doors/settings/emergency` (the Doors screen's details reads, DOOR-7/8; both need Access 1.24.6 or later), `PUT /doors/{id}/lock_rule` (lock, always `lock_now`, and the temporary rules `keep_lock`, `keep_unlock`, `custom` minutes and `reset`; DOOR-7 — the client also covers the documented `lock_early`, which the app never sends), `PUT /doors/settings/emergency` (lockdown / evacuation of all doors, DOOR-8), and the notifications WebSocket `wss://<console>:12445/api/v1/developer/devices/notifications` (DOOR-6). The three PUTs change physical door state: each has exactly one caller in main and is sent once per action the user confirmed (DOOR-3/4). Until P5.6 the lock-rule and emergency calls were in the client with no caller.
- **Implemented in the client, not called by the app:** `GET /doors/{id}`.
- **A door's lock rule is a type and an end time, nothing else.** `GET /doors/{id}/lock_rule` answers `{ type, ended_time }` (`schedule`, `keep_lock`, `keep_unlock`, `custom`, `lock_early`; `ended_time` in Unix seconds). The document gives no name and no hours for a door's unlock schedule and no call that lists one; its §5 schedules belong to access policies (checked against the PDF, 2026-11-18). What a door with no rule answers is undocumented, so the type is parsed as a plain string and an unlisted value is shown as it is (DOOR-7).
- Responses: envelope `{ code, msg, data }` with `code: "SUCCESS"` on success and a `CODE_*` value otherwise. Door fields, error codes and the documented HTTP statuses: the reference extract; types and zod schemas: `src/main/access/types.ts`.
- **Push (DOOR-6).** The notifications socket documents three events: a doorbell ringing, a doorbell status change, and `access.data.device.remote_unlock` (an admin's remote unlock, with the door id). It documents **no relock event and nothing that carries the lock relay**, and does not say whether a card, PIN or schedule unlock is pushed. The app therefore treats every frame only as a reason to read `GET /doors` now, and polls regardless. The socket reconnects with backoff (1 s doubling to 60 s); its failures are logged and do not move the Access status. The HTTP client (undici 7) reports a refused upgrade with no status, so a 401 or 403 on the socket cannot be told from a network failure: a rejected token is caught by DOOR-6's `GET /doors` instead, which stops the socket with it. Webhooks (which do cover every unlock) are not used: they need the console to connect *into* the app.
- **Client rules (P0.4 §3/§5, still in force):** an error is HTTP non-2xx **or** `code !== "SUCCESS"`, whatever the status — the reference lists statuses and codes but not which status goes with which code. A 401 is an auth error whatever the body. Show `msg` when it is present and fall back to the `code` plus the HTTP status when it is not, so a DOOR-3 failure never surfaces an empty message.
- **Schema leniencies**, kept because the reference itself is inconsistent: `is_bind_hub` is "String" in its tables and a boolean in every sample, so both `true`/`false` and `"true"`/`"false"` parse to a boolean; `door_position_status` is `null` in the text and `""` in a sample, and both mean "no sensor"; the envelope's `msg` is optional while `code` stays required. `npm run spike:access` prints a **shape note** for every normalization it would apply, so OS-1 records which form the console really sends.
- **No throttle of our own.** The reference names HTTP 429 but documents no limit and no `Retry-After`, and R9's measured 10 req/s belongs to the *Protect* key. The client does not pace or retry. Two things repeat: DOOR-6's `GET /doors`, at most once a second and only while a linked door is on the Live screen or the Doors screen is open; and, only while the Doors screen is open, DOOR-7's details round — one emergency read plus one lock-rule read per door, strictly one request at a time, every 10 s at the fastest setting (default 30 s), plus, after a door action or a relay change, one coalesced read of only the doors it touched plus the emergency status (an emergency change reads everything). The floors of DOOR-9's ranges are what stands in for a limit. If OS-1 finds a real one, DOOR-9's settings and bounds are where it is absorbed.
- **TLS pinning is per host:port.** The certificate the console presents on 12445 may differ from the one on 443, so the Access pin is kept separately from the Protect pin (P0.4 §4). The notifications socket uses the same host:port and so the same pin.

**Development mock (built in P0.4, extended in P5.5 and P5.6).** The Access client is built and tested against a local mock server (`npm run mock:access`). Since P5.5 it follows the official reference: base path, Bearer auth, the response envelope, the door object, unlock, lock rules, emergency status, the error cases (including an unlock refused for a door with `is_bind_hub: false`) and the notifications WebSocket, which pushes `access.data.device.remote_unlock` on an unlock and, like the documented API, nothing on relock. It serves HTTPS with a self-signed certificate, so the same TLS pinning path is exercised. Where the reference is silent (the HTTP status for each error code, how lock rules and emergency modes interact with unlock) the behaviour is the mock's own choice and marked as such. Mock-only routes under `/__mock/` unlock, lock or move a door without the app, to show DOOR-6 following a change made elsewhere, and (P5.6) `POST /__mock/doors/{id}/schedule` puts a door inside an unlock schedule — the API has no call that creates one — so the Doors screen has a `schedule` rule to show and Lock's `lock_now` a schedule to end (`docs/spikes/P0.4-access-mock.md`). Every mock response carries the header `x-view-protect-mock: 1`, which is how the spike tells a mock target from a real console. The same `npm run spike:access` script runs against the mock now and against the real console on-site (OS-1). **Nothing in §5.2 has run against Access hardware.**

### 5.3 Streaming pipeline (verified end to end in P0.5)

Protect RTSPS → **go2rtc** (bundled, bound to 127.0.0.1 only) → MSE over WebSocket → Chromium `<video>` with hardware decode. Each camera/quality pair is one go2rtc stream. go2rtc keeps **one upstream connection per stream** however many cells consume it, and connects lazily when a consumer appears. See `ARCHITECTURE.md` for the design and `docs/spikes/P0.5-video.md` for the measurements; the pipeline was confirmed in that spike against go2rtc v1.9.15 and its tagged source, on macOS (2026-11-12) and Windows (2026-11-13). **Platform coverage differs:** the process, auth, ownership and renderer-isolation rules and the latency figures hold on both, while the real-stream H.265 pass, the 5 s GOP and its buffer-trim stall, and the ~4 MB keep-window cost were measured on macOS only — the Windows run was H.264 (R1).

**Source URL transform.** The URL from `rtsps-stream` must be rewritten before go2rtc can use it:

```
Protect:  rtsps://<console-host>:7441/<alias>?enableSrtp
go2rtc:   rtspx://<console-host>:7441/<alias>
```

`?enableSrtp` must be **stripped** or go2rtc cannot open the stream; other query parameters are kept. `rtspx` is go2rtc's TLS RTSP scheme with **certificate verification off**, and go2rtc cannot pin a certificate. The app therefore only passes sources whose host equals the pinned console host. **The RTSPS leg itself is not certificate-pinned** (R4); host equality plus loopback binding is the whole mitigation.

**go2rtc process contract.** Modules `api`, `ws`, `rtsp`, `mp4` only (no `webrtc`/`homekit`/`srtp`/`rtmp`). The API listens on `127.0.0.1:<free port>`. The RTSP **server** is off (`rtsp.listen: ""`) while the RTSP **client** still works. `allow_paths` is limited to `/api`, `/api/ws` and `/api/streams`, so there is no web UI, no `/api/config` and no `/api/exit`. Confirmed during a run that go2rtc's only listening socket is that loopback API port, plus one outbound connection to the console on 7441.

**go2rtc API auth.** Loopback-only is not enough: another local process, or a page using DNS rebinding, could otherwise read `/api/streams` or attach to `/api/ws` and watch a camera. So every launch generates a random `api.username` / `api.password` **and sets `api.local_auth: true`** — without `local_auth` go2rtc exempts loopback clients and the credentials do nothing. The config file is written `0600` and deleted as soon as the API answers (go2rtc keeps it in memory). Credentials are never persisted or logged, and go into the log redactor.

**Renderer isolation.** Main injects `Authorization: Basic …` and rewrites `Origin` to `http://127.0.0.1:<port>` in `session.webRequest.onBeforeSendHeaders`, filtered to `ws://127.0.0.1:<port>/*` and `http://127.0.0.1:<port>/*` only, so the renderer only ever gets the port and the stream name. The rewrite is required: go2rtc's default origin check accepts a WebSocket only when the `Origin` host equals the `Host`, which rejects both `Origin: file://` and the dev server's origin. **Never set `origin: "*"`** — any website open in the user's browser could then connect to the loopback port and watch the cameras. Handle `app.on('login')` so a wrong header cannot turn into an auth prompt.

**Listener ownership.** The free-port lookup and go2rtc's bind are not atomic, and go2rtc keeps running without a listener if the bind fails, so after start the app must confirm the port is its own: authenticated `GET /api` → 200, unauthenticated `GET /api` → 401, and the listening PID equal to the child's PID (`lsof` on macOS, **mandatory**; `netstat -ano` on Windows, best effort). On failure, kill the child, delete the config and retry on a new port, up to 3 attempts.

**Player.** MSE over WebSocket into a Chromium `<video>`. Hardware decode verified on both platforms: `VideoToolboxVideoDecoder` (macOS) and `D3D11VideoDecoder` (Windows), both with `platform=true` and GPU `video_decode` enabled. H.265 was verified **on a real stream on macOS** (`hvc1.1.6.L153.B0`, 2688×1512); on Windows only the HEVC capability probes are positive (see R1). Audio is AAC-LC (`mp4a.40.2`) decoded in software by `FFmpegAudioDecoder`, which is normal for audio in Chromium. Cameras may advertise two audio tracks (AAC 16 kHz mono and Opus 48 kHz stereo); go2rtc's MSE consumer picks AAC.

**Buffer-trim requirement (carries into P2.3).** Protect's `high` stream has a keyframe every ~5.0 s. MSE coded-frame removal means the player's default 5 s keep-window also removes every frame up to the next keyframe, which starves the video track: `high` stalls after about 4.4 s with `DEMUXER_UNDERFLOW` while audio keeps playing (`medium` and `low` are unaffected, and go2rtc delivers every packet, so this is purely a player fault). The player must keep **at least 2× the longest GOP** (15 s covers Protect's 5 s) or trim only up to the last keyframe before `currentTime`. Do this by subclassing `VideoRTC` and overriding `onmse()`, leaving the vendored file unmodified. Memory cost at `high` is about 4 MB per player.

**Latency (NFR-5).** The player steers `playbackRate` towards a ~1 s buffer; measured `buffered.end − currentTime` was 0.99–1.02 s mean with p95 ≤ 1.07 s on both platforms. First frame arrived 0.28–0.65 s after the WebSocket connect, which includes the lazily opened upstream RTSPS session. A rough glass-to-glass read gave ~1.5 s ± 1 s, which fits NFR-5 but needs a proper method in P2.5; the ~1 s player buffer is the biggest adjustable part.

**Codec detection (R7).** go2rtc's `/api/streams` reports the producer's codec, so main or the player can tell H.265 from H.264 per stream at runtime. This is the mechanism R7 asks for, and the `--list` mode of the video spike already uses it. The player (P2.3/P2.4) asks `MediaSource.isTypeSupported` about the mime go2rtc's MSE handshake offers and keeps the verdict **per quality**, because a codec belongs to one `<cameraId>_<quality>` stream: a `high` that will not decode never stops a `low` that does. When the asked-for quality is undecodable the cell keeps — and reconnects — the quality it was last showing; only when nothing decodable has been shown does it say "Codec not supported". go2rtc refusing the handshake because none of the codecs the player offered matches the camera's (its `codecs not matched` error, e.g. an H.265 camera where only H.264 could be offered) is the same verdict, not a stream error; only that fact is read from the error, never its text. A refused quality is not retried until go2rtc restarts (every verdict clears) or the cell's quality is changed to it again (that quality's verdict clears, so switching away and back is a one-attempt retry).

**Start-up failures (NFR-7).** A layer whose socket stays open but never plays is retried on the same backoff as a closed socket, in two cases: go2rtc answers the handshake with `{type: 'error'}` (other than the codec mismatch above), or no frame has painted within **10 s of visible time** after attach (`playerTiming.FIRST_FRAME_TIMEOUT_MS`). Time while the window is hidden or minimised does not count, because Chromium does not run the first-frame callback then; without that rule a hidden window would retry every waiting cell every 10 s. The 10 s is not P0.5's cold 0.28–0.65 s: a consumer joining a go2rtc producer that is already running (another cell, or the other swap layer, on the same stream) waits for the next keyframe, up to the ~5 s `high` GOP, so the window is about twice that. While nothing is on screen the cell says "Stream could not start" — only for a layer that never played; a playing stream that errors is handled as a lost socket that keeps its last frame. go2rtc's error text is never shown or logged, because it can contain the source RTSPS URL (CON-2, NFR-9).


### 5.4 Perf mode (development only, P2.5)

The perf harness (`npm run perf`, `scripts/perf/run.ts`, `src/main/perf/`) runs the built app in a measuring mode. Results and the method are in `docs/perf-results.md`.

- **When:** only when `VP_PERF_QUALITY` (`low`/`medium`/`high`) is set **and** the app is unpackaged. A packaged build ignores every `VP_PERF_*` variable. The others are `VP_PERF_DURATION_S`, `VP_PERF_WARMUP_S`, `VP_PERF_INTERVAL_S`, `VP_PERF_OUT` (absolute output directory) and `VP_PERF_LABEL`; invalid values stop the app at launch.
- **Auto-connects:** an explicit exception to CON-4's "nothing connects on launch", independent of `console.connectOnLaunch` (CON-4's own launch connect is skipped during a perf run, so it never races the harness's). Starting the harness is the user's deliberate action, so main calls `connect()` itself, then opens the Live screen and picks the temp-grid preset by clicking its buttons. From P3.2 the temp grid is gone and the harness picks a View instead.
- **Grid quality:** the run's quality replaces `settings.streams.defaultGridQuality` in the settings the renderer is *shown* (IPC `AppState`), in memory only. The stored config is never changed and no save can persist the override.
- **Never writes Views:** from P3.2 the renderer is shown only the in-memory perf View. While it is set, main refuses every View write (`setViews`, `setLastView`) with `bad-request`, so nothing done in the window during a run can store the perf View over the user's Views.
- **Ends by itself:** after the warm-up and the measured duration (or early on a closed window, a quit request, a crashed renderer or a signal) it writes its results, stops go2rtc and quits. Nothing it records or prints contains a URL, the console address, the go2rtc port, a credential or a camera name (CON-2, NFR-9).

## 6. Data model (persisted)

```jsonc

        { "col": 0, "row": 2, "colSpan": 1, "rowSpan": 1, "cameraIds": ["camF"] },

  "accessPolling": { "withSocketSec": 5, "withoutSocketSec": 2, "unlockedSec": 1, "detailsSec": 30 }   // DOOR-9: Access read intervals, whole seconds

```

**Tiling rule (VIEW-1):** every cell lies inside the grid (`col + colSpan ≤ cols`, `row + rowSpan ≤ rows`, spans ≥ 1) and every slot is covered by exactly one cell. Cells are stored sorted by `(row, col)`. `aspect.w` and `aspect.h` are positive; `gap` is 0–64.

**`showNames`** (VIEW-8, P4.3) defaults to `true`; a file written before the field existed loads with the default, so no `schemaVersion` bump or migration was needed (as with `connectOnLaunch`).

**Migration 1 → 2** (`src/main/config/migrations.ts`): v1 stored exactly `cols * rows` cells in row-major order. Cell `i` becomes a 1×1 cell at `col = i % cols`, `row = ⌊i / cols⌋`; `aspect` and `gap` take their defaults (16:9, 0).

**`accessPolling`** (DOOR-9, P5.6) holds the four Access read intervals in whole seconds: `withSocketSec` 2–60 (default 5), `withoutSocketSec` 1–30 (default 2), `unlockedSec` 1–10 (default 1), `detailsSec` 10–600 (default 30). It is read leniently: a missing, non-integer or out-of-range value loads as that field's default (not clamped), and a missing or malformed block as all four defaults, so a file written before P5.6 loads with P5.5's intervals and no `schemaVersion` bump or migration was needed. The strict check is the IPC one (`vp:doors/polling`, §6.1), which refuses instead. The values are used only while Access is on (DOOR-0).

**`console.host` and `console.accessBaseUrl`** (the rules `src/main/console/endpoints.ts` encodes, added in P1.3/P1.4). `host` is an IP or host name and may carry a non-default port (`udm.local:8443`); a scheme other than `https://` is refused rather than upgraded, since the API key may only travel over TLS (CON-2, R5), and an IPv6 literal needs brackets to tell the address from a port. `accessBaseUrl` is the **API root** — origin *and* path, the same value the P0.4 spike takes as `VP_ACCESS_BASE_URL` — so the §5.2 alternative behind the console proxy and the local mock are both just a different value here. `null` derives `https://<console.host>:12445/api/v1/developer`, **ignoring any port in `host`**, because the developer API has its own.

**`console.connectOnLaunch`** (CON-4) is written by main only — it is not part of the Settings form's `vp:console/set` input — `true` once a connect's devices feed has opened, and back to `false` on a cleared or replaced Protect key or a console change that moves the Protect endpoint. It is written only when it changes, not on every reconnect. Default `false`; a file written before the field existed loads with the default, so no `schemaVersion` bump or migration was needed.

**Two certificate fingerprints, not one:** pinning is per host:port (§5.2, P0.4 §4), and the Access developer API answers on 12445 while Protect is behind 443, so `certFingerprint` pins the console and `accessCertFingerprint` pins the Access endpoint; both are `null` until the user accepts them (CON-3). The schema is validated with zod on load. Unknown or older `schemaVersion` values go through migrations in `src/main/config/migrations.ts`.

### 6.1 What crosses IPC (P1.5, streams added in P2.2, Views in P3.1, stream qualities in P3.7, snapshot channel in P5.2, doors in P5.3, door state in P5.5, the Doors screen in P5.6)

The contract is `src/shared/ipc.ts`: one zod schema per request and per reply, validated in the preload *and* again in main. Three rules decide what may be in it.

**No secrets, ever** (CON-2, NFR-9). The API key, the Access token and every RTSPS URL stay in main. The renderer receives two booleans saying whether each credential is stored, the camera models of §5.1 trimmed to the shared `Camera`, snapshot **bytes**, door models, and — from Phase 2 — a stream handle per camera/quality pair: the go2rtc stream name `<cameraId>_<quality>`, the loopback port, the `ws://127.0.0.1:<port>/api/ws?src=<name>` URL built in main, and go2rtc's restart counter (`epoch`); and — from P3.7 — whether each RTSPS quality exists on a camera, as booleans. Never the RTSPS URL and never go2rtc's API credentials — main injects those into the WebSocket in `onBeforeSendHeaders` (§5.3), so the renderer plays a stream it can neither authenticate nor name on its own. The certificate fingerprints do cross: they are public values from a plain-text file, not secrets.

**Failure is a value, not a throw.** Every call answers `{ ok: true, value }` or `{ ok: false, error }`, where the error is a `kind` the UI can branch on plus one sentence written for a person — no stack, no cause chain, no URL and no query string. One `kind` is about the local gateway rather than the console: `gateway-down` means go2rtc is not up (crashed, restarting, or never started), is always retryable, and is deliberately distinct from CAM-3's camera-offline placeholder and from a Settings problem, because the camera is fine and nothing in Settings fixes it. An exception thrown out of a handler would otherwise reach the renderer as main's stack glued to a string, which is both useless to the UI and the easiest way to leak a path.

**Every mutation answers with the whole app state.** Saving a host, storing a key or accepting a certificate changes several things at once (the pin, what is resolvable, whether Access is on), so main returns the new truth rather than having the renderer patch its own copy and drift.

**Views (P3.1).** `vp:views/set` takes the whole View list plus `lastViewId`; main validates it with the View schema, tiling rule (§6) included, and unique View ids, and answers with `AppState` like every mutation. `vp:views/active` takes only `lastViewId`, so switching Views (VIEW-4) does not resend every View.

**Stream qualities (P3.7).** `vp:streams/defaults` takes both QUAL-1 defaults, `{ defaultGridQuality, defaultFillQuality }`: both required, both a `Quality` (never `package`), nothing defaulted, so a renderer bug cannot silently reset the other one. It answers with `AppState` and is refused during a perf run. `vp:cameras/rtsps` takes `{ cameraId }` and answers `{ high, medium, low, package }` as booleans: main reduces `GET rtsps-stream`'s URLs to "is there one" before replying, so no RTSPS URL crosses (QUAL-7).

**Snapshots (P1.7, package channel in P5.2).** `vp:cameras/snapshot` takes `{ cameraId, highQuality, channel? }` and answers the JPEG bytes (or CAM-3's "unavailable"). `highQuality` (default false) is sent to the console only for a camera with `supportsFullHdSnapshot`; `channel` is `main` (the default, never sent) or `package`, and `package` is sent only for a camera with `hasPackageCamera` (CAM-4). Main checks both flags against its inventory, with a log line when one does not hold: `highQuality` is dropped (a smaller image is still the right answer), while `channel=package` for a camera without a package camera — or one the inventory does not know — is answered as CAM-3's "unavailable" with nothing fetched, since the main channel's image would be the wrong picture. The app asks for the package channel only from the View editor (VIEW-3).

**Doors (P5.3).** P5.3's one-shot `vp:doors/list` was removed in P5.6 (user decision 2026-11-18; DOOR-1): the door list reaches the renderer only through `vp:doors/screen` below. `vp:doors/links` takes `{ links }`, the whole `{ cameraId: doorId }` map with non-empty keys and values and **no default** (a missing map would otherwise erase every link), replaces `doorLinks`, and answers with `AppState`. Main checks the map against neither the inventory nor the door list (DOOR-2: links are never pruned), and a perf run does not block it, since the harness never changes the links the renderer is shown. Since P5.6 `vp:doors/links` is sent from the Doors screen's cards.

**Unlock (P5.4).** `vp:doors/unlock` takes `{ cameraRef }` — a cell's camera ref, `<cameraId>` or `<cameraId>:package` — and answers `{ doorId, cameraName, outcome: "unlocked" | "unknown", reason }` (`reason`, the safe error text, only for `unknown`: a timeout or a connection lost after connecting, DOOR-3). Main strips `:package` (the package channel shares the doorbell's link, DOOR-2), reads the door from `doorLinks`, and answers `disabled` with no call while Access is off (DOOR-0, checked first), `not-found` with no Access call when there is no link, and otherwise sends exactly **one** `PUT /doors/{id}/unlock`. It answers without waiting for the log write. It never retries, and every unlock failure is `retryable: false` whatever its kind (a door the console refuses to release, e.g. one without a Door Hub, arrives as `auth` like the other Access refusals; its message names both causes). The Access status follows the unlock: `connected` on success and on a refusal about the door itself (the console answered), `error` on other failures; no link and Access off leave it alone, since a second request is a second door release (DOOR-3/4). `cameraName` comes from main's inventory (the id when it does not know the camera). Every attempt goes to `unlock.log` (DOOR-5).

**Door state (P5.5).** `vp:doors/watch` takes `{ watching }` and answers the linked doors' states main knows at that moment, `{ "<doorId>": { relay, position } }` (often empty on the first call). `true` starts main's watching and `false` stops it (DOOR-6); the renderer names no door, main watches the doors in `doorLinks`. It answers an empty map, with no Access call, while Access is off (DOOR-0), with no token or with no links. Changes arrive as the `doorStates` push, always the **whole** map: a linked door missing from it is unknown. A reload or loss of the renderer ends the watching; the Live screen asks again when it mounts.

**Doors screen (P5.6).** `vp:doors/screen` takes `{ open }` and answers the Doors screen's state as main has it at that moment, `{ doors, stale, rules, emergency, error }`:

- `doors`: the trimmed `Door` list main last read from the **current** Access endpoint, or `null` — nothing read yet, the screen closed, the reading stopped, or the console, a certificate or the token changed. It is also the list a door action's id is checked against (DOOR-4).
- `stale`: `true` once two reads in a row have failed. The list is kept, but every relay and position in it is old and must be drawn as unknown (DOOR-7), and main refuses door actions while it is `true` (DOOR-4).
- `rules`: `{ "<doorId>": { type, endedTime } }`, `endedTime` in Unix seconds or `null`. A door **missing** from the map has an unknown rule; `type: ""` is the console reporting none.
- `emergency`: `{ lockdown, evacuation }`, or `null` when it is not known (DOOR-8).
- `error`: why the list cannot be read, as the usual error value — the last failed read, or the reason nothing is being read (`disabled`, `not-configured`, `auth` for a missing or rejected token, `pin-required`, `pin-mismatch`, a network kind) — and `null` once a read works. With `doors: null` the reason is set at once; while there is a list, a failing read is reported **only together with `stale`**, from the second failure in a row (user decision 2026-11-18).

`true` makes the door-state monitor run for the screen and watch every door (DOOR-6); `false` ends that and answers the all-unknown state (`doors: null`, `stale: false`, `rules: {}`, `emergency: null`, `error: null`). Like `vp:doors/watch` it never fails for a console reason, and while Access is off it makes no Access call and the state carries the `disabled` error (DOOR-0). Changes arrive as the `doorsScreen` push: always the **whole** state, only on a change and only while the screen is open. When the reading stops with the screen still open, one last push says so (`doors: null` and the reason in `error`); closing sends no push, the `open: false` answer being the reset. A reload or loss of the renderer closes it.

**Door actions (P5.6).** `vp:doors/action` takes `{ doorId, action, minutes? }` — `doorId` a string of 1 to 200 characters (longer is refused by the schema as `invalid-request`: a refused id is logged as received, DOOR-5); `action` one of `unlock`, `lock`, `keep_unlock`, `keep_lock`, `custom`, `reset`; `minutes` a whole number from 1 to 1440, required for `custom` and refused with any other action — and answers `{ doorId, doorName, action, sent, minutes, outcome: "done" | "unknown", reason }`. `sent` is what main sent: `unlock` (`PUT /doors/{id}/unlock`) or the type of the `PUT /doors/{id}/lock_rule` — `lock_now`, `reset`, `keep_lock`, `keep_unlock`, `custom`; for `lock` it is always `lock_now` (DOOR-7, user decision 2026-11-18), and `reset` only for the `reset` action. `doorName` is the door's full name, then its name, then the id, from main's list; `minutes` is the `custom` duration, else `null`; `reason` is the safe error text for `unknown`, else `null`. Main's refusals, in this order and each with **no Access call**: `disabled` while Access is off (DOOR-0); `not-found` for a door id that is not in the list main itself last read while the Doors screen is open (DOOR-4); `unavailable` while that list is stale (two door reads in a row have failed, DOOR-4); `bad-request` for a door with no hub, whatever the action. Otherwise it sends exactly **one** PUT: never retried, every failure `retryable: false` whatever its kind, and a PUT that may have reached the console with no answer (a timeout, or the connection lost after connecting) is `ok` with `outcome: "unknown"`. The Access status follows it as it follows an unlock: `connected` on success and on a refusal about the door or the request (the console answered), `error` otherwise, an unknown outcome included; an answer for an endpoint the user has replaced meanwhile leaves the new endpoint's status alone. After the answer main reads the doors, that door's lock rule and the emergency status at once — reads only.

`vp:doors/emergency` takes `{ lockdown, evacuation }`, both required and **not both `true`** (refused by the schema as `invalid-request`, like any malformed payload; main repeats the check as `bad-request`), and answers `{ lockdown, evacuation, outcome: "done" | "unknown", reason }` with the flags as sent. It answers `disabled` with no call while Access is off, and otherwise sends one `PUT /doors/settings/emergency` under the same rules as a door action; there is no door id to check, so main looks neither at whether the Doors screen is open nor at whether its door list is stale (coordinator decision 2026-11-18, DOOR-7). Every attempt that reaches either handler, main's refusals included, is a line in `unlock.log` without the answer waiting for the write (DOOR-5); a payload the IPC layer refuses is not. Neither call is blocked by a perf run, as for `vp:doors/unlock`.

**Polling settings (P5.6).** `vp:doors/polling` takes `{ withSocketSec, withoutSocketSec, unlockedSec, detailsSec }` — all four required, whole seconds, each inside its range (DOOR-9), **nothing defaulted**, so a renderer bug cannot silently reset an interval the user did not touch — replaces `accessPolling`, has the monitor re-arm its timers, and answers with `AppState`. It makes no Access call, is accepted while Access is off like `vp:doors/links`, and is not blocked by a perf run.

Main pushes six things, and only these: the linked doors' lock states while the Live screen watches them (DOOR-6), the Doors screen's state while that screen is open (DOOR-7), the connection status (CON-5), the whole camera inventory after each connect, reconnect or add/remove (CAM-2 — `GET /v1/cameras` stays the authority, because the devices feed's shapes are unverified, R11), single camera `state` changes, which is the path gate G1 times at ten seconds, and — from Phase 2 — the go2rtc runtime: up on a port with an epoch, or down. go2rtc takes a new free port every launch, so a handle from an earlier epoch is dead; the push is what lets a player re-ask for its stream instead of inferring a restart from a closed socket (gate G2).
