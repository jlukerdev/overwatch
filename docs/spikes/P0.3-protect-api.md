# P0.3 — Protect Integration API spike

**Date:** 2026-11-12 · **Script:** `npm run spike:protect [-- --listen <sec>] [--post-camera <name|cam-NNN> [--allow-second-camera]]` (`scripts/spikes/protect-spike.ts`) · **Fixtures:** `tests/fixtures/protect/` · **Contract:** `docs/reference/protect-openapi-v7.3.74.json`

Three runs against the UDM SE: 120 s, 300 s and 120 s of WebSocket listening (9 minutes in all). An earlier attempt was rate limited (see §7), which is how the limit was found. After the code-review fixes, one more read-only run (`--listen 30`, no POST) confirmed the new behaviour below.

## Running the spike

- `npm run spike:protect` is **read-only**. It GETs `rtsps-stream` for every connected camera, prints which qualities are `null`, and runs the stream and snapshot checks on a camera that already has streams (all three preferred). It never POSTs.
- `npm run spike:protect -- --post-camera <name|cam-NNN>` also allows `POST /v1/cameras/{id}/rtsps-stream` on **that camera only**, and only for qualities a fresh GET shows as `null`. The spike never picks a camera to write to by itself. `cam-NNN` is the fake id printed in the camera table.
  - The camera is recorded in `scripts/spikes/output/posted-camera.json` (gitignored; it holds the raw camera id) **before** the POST. A later `--post-camera` naming a different camera exits with code 1, unless `--allow-second-camera` is passed.
  - A POST is never retried as is. On a 429 the spike waits `windowMs`, re-GETs, and makes **at most one** more POST for the qualities that are still `null`. A second 429 stops the run with a message.
- **TLS pin:** the first run with no pin saves the leaf SHA-256 to `scripts/spikes/output/console-pin.json` (gitignored) and prints `trusting on first use`. Later runs enforce that pin. `VP_CONSOLE_FINGERPRINT` in `.env.local` overrides the file. On a mismatch the run stops; to re-pin, delete `console-pin.json` or set `VP_CONSOLE_FINGERPRINT` to the new fingerprint. The run prints the pin source (`VP_CONSOLE_FINGERPRINT`, `saved pin`, or `first use`).
- **WebSockets:** if either socket closes before the listen period ends, the run reports which one, with its close code and reason, and stops waiting once both are closed. If the events socket closed early, the run says that the absence of motion is not meaningful.
- **Motion capture re-run:** `npm run spike:protect -- --listen 300`, with someone walking in front of a G3 Instant (see §5).

## 1. Auth (R6) — resolved

- A **locally created key** (UniFi OS → Settings → Control Plane → Integrations) works on the local endpoint: `https://<console>/proxy/protect/integration/v1/...` with header `X-API-KEY`. No unifi.ui.com key was needed.
- The same header authenticates both WebSockets (`wss://<console>/proxy/protect/integration/v1/subscribe/{devices,events}`). There is no subprotocol and no extensions.

## 2. Version and cameras

- `GET /v1/meta/info` → `applicationVersion: "7.3.74"`. This matches the vendored contract.
- `GET /v1/cameras` → **9 cameras, all `CONNECTED`**: 3× G3 Instant, 4× G4 Instant, 1× G4 Bullet, 1× G5 Flex.
  - All 9: `hasMic: true`, `isMicEnabled: true`, `hasPackageCamera: false`, `guid: null`.
  - `hasSpeaker`: 7 true (the G3/G4 Instants), 2 false (G4 Bullet, G5 Flex).
  - `featureFlags.smartDetectTypes`: `person, vehicle, animal` on the 6 G4/G5 cameras, empty on the G3 Instants.
  - `featureFlags.supportFullHdSnapshot`: true only on the G4 Bullet.
  - No doorbell, so `package` and `ring` could not be exercised.

## 3. `rtsps-stream`

- `GET` returns `{ high, medium, low, package }`, with each one a URL or `null`, as the contract says. Before the spike, 4 of the 9 cameras already had a `medium` stream and nothing else. That is probably another integration (e.g. Home Assistant), and it's why the app must never DELETE streams.
- **POST happened once, on one camera** (a G4 Instant that had only `medium`): `{"qualities":["high","low"]}` → 200 with `{ high, low }`, and only the requested keys came back. The follow-up GET showed all three. Later runs picked the same camera, found all three present and made no POST. (Those runs predate `--post-camera`, so that camera is not in `posted-camera.json`. Pass its fake id to `--post-camera` if it ever needs another POST.)
- `medium` worked: a pre-existing stream, it was reused, and it was left unchanged by the POST.
- **URL shape:** `rtsps://<console-host>:7441/<16-char alias>?enableSrtp`. Each quality has its own alias. The host is the console address the API was called with.
- **Stability:** URLs are identical across repeated GETs within a run and across the POST (existing URLs untouched). The URLs returned by POST equal those returned by the next GET. Later runs found the same three streams still present. The spike does not keep URLs between runs, so it did not check that their values were unchanged.
- Calls take about 10–25 ms. POST took about 75 ms.

## 4. `snapshot`

- Default: `200 image/jpeg`. On a G4 Instant it was 640×360, about 32 KB, in about 300 ms.
- `highQuality=true` on a camera **without** `supportFullHdSnapshot` → **`400 {"error":"Camera does not support full HD snapshot","name":"BAD_REQUEST"}`**. It does not quietly fall back to a smaller image.
- On the G4 Bullet (`supportFullHdSnapshot: true`), both default and `highQuality=true` returned a 2688×1512 JPEG of about 1.1 MB in 0.5–0.7 s. So on that camera the default is already full resolution.
- **503 (camera offline) was not observed:** every camera was online. This is still unverified.
- Images were saved only to `scripts/spikes/output/` (gitignored, checked with `git check-ignore`). `snapshot.meta.json` holds only status, content type and size.

## 5. WebSockets

- **Devices** (`/subscribe/devices`): it opened fine, but **0 messages in 9 minutes**. No initial snapshot is sent on connect, so the app must load the inventory with `GET /cameras` and treat this socket as change notifications only. No device changed during the runs, so no `devices-ws.sample.json` was produced, and the `deviceEvent` shape is still unverified.
- **Events** (`/subscribe/events`): 70 messages in 3 runs, **all `smartDetectZone` (person)**, from all 5 G4 cameras (none from the G5 Flex or the G3 Instants). All of them passed contract validation.
  - Sequence per event: `add` → quick `update` (+0.1–0.4 s, no `end`) → … → `update` with `end` set, which is then **repeated two or three times** (identical payloads 0–0.5 s apart). Consumers must be idempotent on `(id, end)`.
  - The `add` item **omits `end` entirely**. It is not `end: null`. The contract allows this (`end` is optional), but SPEC §5.1 says "`end` null".
  - `update` items are full event objects (`id, modelKey, type, start, device, smartDetectTypes[, end]`), not partial ones.
  - Timing example: the event's `start`→`end` was 9.5 s. The `end` update arrived about 13.5 s after the `add`, so about 4 s after the `end` timestamp. Expect an end signal 3–5 s after the scene goes quiet.
  - **`motion` events (re-test, 5 min):** the first runs saw no `motion` because **motion detection was disabled on every camera** in Protect. With it enabled on Front Yard (G4 Instant) and Backyard (G4 Bullet), walking past each produced 6 complete `motion` events (3 per camera) alongside `smartDetectZone` (person) events for the same walk. So `motion` is **not** suppressed on smart-detect cameras: it fires only when the camera's *motion detection* setting is on, independently of smart detection.
  - Motion sequence: `add` (no `end`) → **a single** `update` with `end` (no repeats seen, unlike smartDetect). Example: start→end 16.6 s, end update received 9.3 s after the add. Events lasted roughly 10–30 s per walk-by. `events-ws.motion.json` now holds a real pair.
  - No `ring`, `smartDetectLine` or `smartDetectLoiterZone` events were seen. There is no doorbell.
- **Keepalive:** in 9 minutes the server sent **no WebSocket pings** (counted through undici's `undici:websocket:ping` diagnostics channel), and the idle devices socket was not closed. The client has to detect dead connections itself (e.g. send its own ping, or reconnect on a TCP error).
- Rate-limited connect: the server accepts the upgrade, sends one JSON text frame `{"error":"Too many requests","name":"TOO_MANY_REQUESTS_ERROR","windowMs":1000,"limit":10}`, then closes with **code 4500**, reason `Too many requests`.

## 6. Contract validation (Ajv 2020-12 against the vendored OpenAPI 3.1 document)

| Endpoint | Samples | Result |
|---|---|---|
| `GET /v1/meta/info` | 3 | valid |
| `GET /v1/cameras` | 3 | **invalid**: every camera lacks `lcdMessage`, which the contract lists as required |
| `GET /v1/cameras/{id}/rtsps-stream` | 33 | valid |
| `POST /v1/cameras/{id}/rtsps-stream` | 1 | valid |
| `GET /v1/cameras/{id}/snapshot` 400 | 3 | valid `genericError` |
| `429` bodies (any endpoint) | 6 | valid `genericError`. **Extra properties `windowMs`, `limit`** |
| WS `/v1/subscribe/events` | 70 | valid |
| WS `/v1/subscribe/devices` | 0 | not exercised (no messages) |

No other undeclared properties were found in any response.

**Implication for P0.3b/P1.3:** generated types will mark `lcdMessage` as required. The client should treat it as optional (none of these cameras has a display), either with a zod/override layer in `types.ts` or by parsing leniently.

## 7. Rate limit (not in the contract)

- **10 requests per 1-second window**, per key. Response headers: `ratelimit: "10-in-1sec"; r=<remaining>; t=<reset s>` and `ratelimit-policy: "10-in-1sec"; q=10; w=1; pk=:<partition key>:`.
  - The `pk` value is an opaque per-client key. Don't log it. The spike logs these headers through an allowlist: the policy name plus the numeric `q`, `w`, `r`, `t`, `limit`, `remaining` and `reset` parameters. Everything else, including `pk`, is dropped.
- Over the limit: `429 {"error":"Too many requests","name":"TOO_MANY_REQUESTS_ERROR","windowMs":1000,"limit":10}`. WebSocket upgrades count against the same budget.
- The spike spaces requests at least 150 ms apart and retries a GET after `windowMs` on 429. A POST is not retried as is (see "Running the spike"). That gave zero 429s afterwards.
- This matters for P1.7/P2.2. Fetching snapshots for 15 cameras, or `ensureStream` for a 10-cell View, at startup will hit the limit unless calls are queued or throttled.

## 8. TLS

- The console presents a **self-signed** leaf certificate, valid Dec 2024 → Mar 2027. Leaf SHA-256: `7B:12:B7:0C:…:B8:5C:B6:6A` (truncated).
- Approach (`scripts/spikes/lib/tls.ts`, mirrors CON-3):
  1. One `tls.connect` with verification off reads the leaf fingerprint. It must match `VP_CONSOLE_FINGERPRINT` if set, else the pin saved in `scripts/spikes/output/console-pin.json`. Only when neither exists is it trusted on first use and saved.
  2. An undici `Agent` uses a custom `connect` that wraps `buildConnector({ rejectUnauthorized: false })`. It compares `getPeerCertificate().fingerprint256` against the pin before handing over the socket, and destroys the socket on mismatch.
  3. The same Agent is the `dispatcher` for both `fetch` and `WebSocket`.
- **Gotcha:** **TLS session resumption must be disabled (`maxCachedSessions: 0`).** On a resumed session `getPeerCertificate()` returns no fingerprint, and the second request failed the pin check. P1.2 needs the same setting, or must verify only on full handshakes and tie resumption to the pinned session.

Dependencies added (dev only):
- `undici@7.30.2`, the same major as Node 24's bundled one. It provides `Agent`/`buildConnector` for the pinned dispatcher, and its `WebSocket` accepts `headers` and `dispatcher`, so the `ws` package was not needed. ARCHITECTURE already plans a pinned undici Agent (P1.2).
- `ajv@8.20.0` and `ajv-formats@3.0.1`, for 2020-12 validation.

## 9. Proposed SPEC §5.1 changes (for P0.6; SPEC not edited here)

1. **Auth:** state that locally created Integrations keys work on the local endpoint (R6 resolved). The same `X-API-KEY` header works on the WebSockets.
2. **Rate limit:** add a row/note: 10 req/s per key, 429 `TOO_MANY_REQUESTS_ERROR` with `windowMs`/`limit`, WS close code 4500. Clients must queue or throttle REST calls (snapshots, `ensureStream`) and back off WS reconnects.
3. **`rtsps-stream`:** URL shape `rtsps://<host>:7441/<alias>?enableSrtp`. URLs are stable across GETs and POSTs, so they can be cached per camera/quality and refreshed on QUAL-8 triggers. POST returns only the requested qualities. Note that other integrations may have created some qualities already (seen: `medium` only).
4. **Snapshot:** `highQuality=true` returns **400** on cameras without `featureFlags.supportFullHdSnapshot`. Only send it when that flag is true. 503 offline is still unverified.
5. **Events:** an event starts with `add` where **`end` is absent** (not `null`). It ends with an `update` that sets `end`; smartDetect end updates may be **repeated** (motion's were not), so handle both idempotently. Updates carry the full event. `motion` only fires on cameras whose Protect **motion detection** setting is on (it was off on all cameras initially), while `smartDetect*` fires whenever smart detection matches. SPEC should note this in CELL-2/settings: auto-switch on `motion` needs motion detection enabled per camera in Protect, and the default trigger set (motion + smartDetect + ring) covers cameras with either setting. The camera object exposes no motion-detection flag in the Integration API, so the app can't detect it; document it as a setup requirement.
6. **Devices WS:** there is no initial state on connect, only changes. Combine `GET /cameras` with the socket, and re-GET after each reconnect.
7. **Keepalive:** the server sends no WS pings. The client must detect dead sockets itself.
8. **Contract drift:** `camera.lcdMessage` is required in the contract but absent on cameras without a display. `genericError` 429 bodies carry `windowMs` and `limit`. Generated types need a small override.
9. **TLS (CON-3):** the pinned connector must disable TLS session resumption, or handle resumed sessions explicitly.
