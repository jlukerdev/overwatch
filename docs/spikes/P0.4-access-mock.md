# P0.4 — UniFi Access mock + spike

**Date:** 2026-11-12 · **Mock:** `npm run mock:access` (`scripts/mock-access/`) · **Spike:** `npm run spike:access [-- --unlock "<door name>" [--yes] [--watch <sec>]]` (`scripts/spikes/access-spike.ts`) · **Types:** `src/main/access/types.ts` · **Fixtures:** `tests/fixtures/access/`

The development network has **no UniFi Access**. Access is an optional feature, off by default (DOOR-0, R3). P0.4 therefore builds:

- a local HTTPS **mock** of the Access developer API, built from community sources, and
- a **spike client** that runs against the mock now and against the real site console on-site (OS-1, §6).

> ⚠️ **Everything in this document about the Access API is COMMUNITY-SOURCED and UNVERIFIED.** Ubiquiti's developer portal does not document Access. Nothing here has been run against real Access hardware. OS-1 is the check, and its results replace these assumptions.

> **Superseded in part (P5.5, 2026-11-18).** Ubiquiti's official reference is now in the repo (`docs/reference/access-endpoints-v4.2.16.md`) and the mock follows it. §1–§5 below are kept as written on 2026-11-12; **§7 says what the reference confirms, contradicts and leaves open, and is the current description of the mock** (all routes, the notifications WebSocket, the mock-only controls). Still true: nothing has been run against real Access hardware.

## 1. What is mocked

*(As of P0.4. The mock has since gained the lock-rule and emergency endpoints, the notifications WebSocket and mock-only controls: see §7.3–§7.6. The rows below still hold, except that `CODE_SYSTEM_ERROR` is a real documented code.)*

Base `https://127.0.0.1:12445/api/v1/developer`, self-signed certificate, Bearer token.

| Request | Mock behaviour |
|---|---|
| any request without `Authorization: Bearer <token>`, or with the wrong token | HTTP 401, `{ "code": "CODE_UNAUTHORIZED", "msg": … }`, as a real console answers (OS-1). Auth is checked before routing |
| `GET /doors` | 200, `{ "code": "SUCCESS", "msg": "success", "data": [door…] }` |
| `GET /doors/{id}` | 200 with one door, or HTTP **200** `CODE_NOT_EXISTS`, as a real console answers (OS-1) |
| `PUT /doors/{id}/unlock` | 200 `{ "code": "SUCCESS", "msg": "success", "data": "success" }`. The door's `door_lock_relay_status` goes to `unlock` for 5 s (`--unlock-ms`), then back to `lock`. A second unlock during the window restarts it |
| unlock (and the other per-door calls), unknown door | HTTP 200 `CODE_NOT_EXISTS` |
| unlock, door with `is_bind_hub: false` | 403 `CODE_OPERATION_FORBIDDEN` (the community docs say remote unlock needs a hub) |
| unlock, body not JSON / not an object / unknown field / `actor_id` without `actor_name` | 400 `CODE_PARAMS_INVALID`, nothing unlocked. An empty body is valid |
| wrong method on a known path | 405 `CODE_RESOURCE_NOT_FOUND` |
| unknown path | 404 `CODE_RESOURCE_NOT_FOUND` |
| `--fail-rate <0..1>` | that share of authenticated requests gets 500 `CODE_SYSTEM_ERROR` (a mock-only code). An injected failure on unlock does not unlock |
| `--latency-ms <ms>` | every response is delayed by that much (timeout handling) |
| **every response** | carries the mock-only header `x-view-protect-mock: 1` (`MOCK_HEADER` in `app.ts`). This is part of the mock contract: the spike treats a target as the mock **only** when it sees this header (§4). The real console does not send it |

Fake doors (`scripts/mock-access/doors.ts`, fixed fake UUIDs): **Front Door**, **Garage Side Door** (position `open`), **Office**, and **Storage Room**, which is deliberately not bound to a hub (`is_bind_hub: false`, position `null`), so unlocking it exercises the error path.

Design:

- `scripts/mock-access/app.ts` holds all request handling as a pure function (`createAccessMock({ token }).handle(req)`), unit-tested in `tests/unit/accessMock.test.ts` with fake timers for the relay revert. `server.ts` only wraps it in `node:https`, reads bodies (64 KiB cap) and logs.
- **Loopback by default** (`--host 127.0.0.1`). Any other `--host` prints a warning.
- **Certificate:** generated on first run into `scripts/mock-access/.cert/` (gitignored, key `0600`) with the system `openssl` (P-256, SAN `localhost`, `127.0.0.1`, `::1`, 825 days). No new devDependency: macOS and Linux ship `openssl`, and on Windows Git for Windows includes it. `--cert`/`--key` take your own PEM files instead. The SHA-256 fingerprint is printed on start. Delete `.cert/` to get a new certificate (then delete the spike's mock pin, §4).
- **Token:** `VP_ACCESS_TOKEN` from the environment, else `.env.local`, is used and never printed. If neither is set, a random token is generated and printed once, labelled mock-only.
- **Logging:** one line per request: time, method, path, HTTP status, result code. Headers (and so the token) are never logged.

## 3. Assumptions (all unverified, check in OS-1)

*(As of P0.4. §7.1 goes through these one by one against the official reference.)*

1. **Base URL** `https://<console>:12445/api/v1/developer`. SPEC §5.2 notes it may also be behind the console proxy on 443 on newer firmware.
2. **Auth** `Authorization: Bearer <token>`; token from Access → Settings → Advanced → API Token. Token scopes may matter (`view:door`/`edit:door`-style). SPEC §5.2's open question (a different auth path for unlock on some firmware) is not modelled.
3. **Envelope** `{ code, msg, data }`, success `code: "SUCCESS"`, `msg: "success"`. No source says `msg` is always present, so the schemas accept it missing (lenient, see below); `code` is required.
4. **HTTP status of errors is not documented anywhere.** The mock picks 401 / 403 / 404 / 400 / 405 / 500, except an unknown door, which gets HTTP 200 with `CODE_NOT_EXISTS` because a real console answers that way (OS-1). **P1.4's client must treat any `code !== "SUCCESS"` as an error whatever the status**, and a 401 as an auth error whatever the body.
5. **Which code a bad token gets.** The guide lists `CODE_AUTH_FAILED`, `CODE_ACCESS_TOKEN_INVALID` ("invalid or expired") and `CODE_UNAUTHORIZED` ("lacks the required permission scope"). The mock uses `CODE_UNAUTHORIZED` for both missing and wrong tokens, which is what a real console sent for a wrong one (OS-1).
6. **Not-exists code.** `CODE_NOT_EXISTS` vs `CODE_RESOURCE_NOT_FOUND`: the mock uses `CODE_NOT_EXISTS` for unknown door ids and `CODE_RESOURCE_NOT_FOUND` for unknown paths.
7. **Door fields** as listed in §2. `is_bind_hub` is typed String in the community table but boolean in its example; the schema accepts both (lenient, see below). `door_position_status` may be `null` or `""` without a sensor; both accepted. `type` has no documented enum.
8. **Unlock** is `PUT` with an empty body, response `data: "success"`. The relay returns to `lock` "after a few seconds"; the mock uses 5 s. The real duration is the door's configured unlock time.
9. **Unbound doors** (`is_bind_hub: false`) refuse remote unlock. The real error code is unknown; the mock uses `CODE_OPERATION_FORBIDDEN`.
10. **`CODE_SYSTEM_ERROR`** is invented for `--fail-rate`; it is not a community-documented code.
11. Pagination (`pagination: { page_num, page_size, total }`) exists on some endpoints; the doors list is assumed unpaginated.

The zod schemas in `src/main/access/types.ts` encode 3, 5–8 and are marked COMMUNITY-SOURCED / UNVERIFIED (OS-1). They strip unknown fields; the spike reports any undocumented keys separately.

**Leniencies** (each marked `UNVERIFIED (OS-1)` in `types.ts`; P1.4 uses these schemas):

- `is_bind_hub` accepts `true`/`false` **and** the strings `"true"`/`"false"`, and always parses to a boolean. Any other value (`"yes"`, `1`, `null`, …) is rejected.
- Envelope `msg` is optional (a string when present), on both the success and the error envelope. `code` stays required.

So that OS-1 learns which form the console really uses, the spike runs a pure check on the raw JSON before parsing (`shapeNotes` in `scripts/spikes/lib/access.ts`) and prints a **shape note** for each normalization it would apply (e.g. `door.is_bind_hub sent as string "true" (normalized to boolean)`, `(envelope).msg absent`). Shape notes appear under each check, in the summary at the end (`shape notes: none …` when nothing was normalized) and in the summary JSON (`shapeNotes`).

## 4. Running the mock and the spike

```bash
npm run mock:access
```
```bash
VP_ACCESS_BASE_URL=https://127.0.0.1:12445/api/v1/developer VP_ACCESS_TOKEN=<token the mock printed> npm run spike:access
```
```bash
VP_ACCESS_BASE_URL=https://127.0.0.1:12445/api/v1/developer VP_ACCESS_TOKEN=<token the mock printed> npm run spike:access -- --unlock "Front Door" --yes
```

If `VP_ACCESS_TOKEN` is set in `.env.local`, both the mock and the spike use it and you can leave it off the command line. Values already in the environment win over `.env.local`. Mock flags: `--port` (12445), `--host` (127.0.0.1), `--latency-ms`, `--fail-rate`, `--unlock-ms` (5000), `--cert`/`--key`.

The spike:

1. **TLS:** the base URL must be `https://` (the Access API is HTTPS-only; an `http://` `VP_ACCESS_BASE_URL` or `VP_CONSOLE_HOST` is rejected with a clear error, and the port is the explicit one or 443). Reads the leaf certificate and pins it (trust on first use) in `scripts/spikes/output/access-pin-<host>-<port>.json` (gitignored). The pin file is keyed by host and port, so the mock's pin, the site console's pin and the Protect spike's `console-pin.json` never collide. `VP_ACCESS_FINGERPRINT` overrides the file. On a mismatch it stops.
2. **`GET /doors`:** classifies the target from this first response: **`mock` only if it carries `x-view-protect-mock: 1`**, otherwise `console`, whatever the host (a loopback address is not proof of the mock). Prints `target: LOCAL MOCK (x-view-protect-mock header present)` or `target: CONSOLE (no mock header)`. Then validates against the zod schema, prints a table of fake ids (`door-001`, `floor-001`), names, relay and position, and writes `doors.json`.
3. **Error probes (read-only):** `GET /doors` with a made-up token → `error-unauthorized.json`; `GET /doors/00000000-0000-4000-8000-000000000000` → `error-not-exists.json`.
4. **Unlock (only with `--unlock "<name>"`):** finds the door by exact name (case-insensitive), then asks you to **type the door name** to confirm (DOOR-3/4). **`--yes` works only against the mock:** if the target was not identified as the mock (step 2), the spike exits 1 right after `GET /doors`, before writing any fixture or unlocking anything, with `--yes is only allowed against the mock; on a real console type the door name to confirm (DOOR-3/4)`. The typed confirmation is mandatory for a console. Without a terminal and without `--yes` it refuses. One `PUT /doors/{id}/unlock` with no body, then it re-reads the door once a second for `--watch` seconds (default 8) and prints each relay change. Writes `unlock.json` with the relay samples.
5. Prints a shape-check summary (schema mismatches, undocumented keys and shape notes) and writes a sanitized summary to `scripts/spikes/output/access-summary-<mock|console>.json`.

Fixtures carry `"_source": "mock"` only when the target was identified as the mock by its header (step 2), `"console"` otherwise. Everything printed or written goes through `scripts/spikes/lib/sanitize.ts` with the token and the target host as literal secrets (the host always, since the classification is only known after the first response; so the pin path prints as `access-pin-<redacted>-<port>.json`); door and floor UUIDs become `door-NNN` / `floor-NNN`. A failed call prints one line with the HTTP status, code and message (exit code 1), never a stack or the token.

## 5. What P1.4 takes from this

- Import types and schemas from `src/main/access/types.ts`; parse every response with them.
- Error = HTTP non-2xx **or** `code !== "SUCCESS"`. Show `msg` to the user.
- Pin TLS through `src/main/tls/` exactly as for Protect; the console certificate on 12445 may differ from the one on 443, so pin per host:port.
- Test against `createAccessMock()` directly (no sockets) and against the running mock.

## 6. OS-1 on-site procedure

Prerequisites: a laptop on the site LAN with this repo, Node 24, `npm install` done; an Access API token created on the site console (Access → Settings → Advanced → API Token) with door view and unlock permissions; an **agreed test door** and someone standing at it.

1. Put the token in `.env.local` as `VP_ACCESS_TOKEN=…` and the console in `VP_CONSOLE_HOST=…` (or set `VP_ACCESS_BASE_URL=https://<console>:12445/api/v1/developer`). Do not set `VP_ACCESS_BASE_URL` to the mock.
2. Optional: get the console's certificate fingerprint from its UI or a trusted channel and set `VP_ACCESS_FINGERPRINT`. Otherwise the first run trusts on first use and pins to `scripts/spikes/output/access-pin-<host>-12445.json`.
3. Read-only run:
   ```bash
   npm run spike:access
   ```
   - It must say `target: CONSOLE (no mock header) (_source: "console")`.
   - If port 12445 does not answer, try `VP_ACCESS_BASE_URL=https://<console>/proxy/access/api/v1/developer` (unverified alternative; SPEC §5.2) and record which worked.
4. Unlock the agreed test door once, typing its name at the prompt (**never `--yes` on-site**):
   ```bash
   npm run spike:access -- --unlock "<test door name>" --watch 15
   ```
   Confirm with the person at the door that it actually released, and note how long the relay stayed `unlock`.
5. **Compare** (the spike's shape-check summary and `scripts/spikes/output/access-summary-console.json` list mismatches and undocumented keys):
   - base URL/port and auth header that worked;
   - envelope keys and the `SUCCESS` / `msg` values;
   - each door field's presence, type and values (`is_bind_hub` boolean vs string: see the shape notes, `door_position_status` `null` vs `""`, `type` values);
   - the HTTP status **and** `code` for the bad-token and missing-door probes (assumptions 4–6);
   - the unlock response body and the real relay duration;
   - any extra keys (e.g. pagination);
   - **(P5.5, read-only)** `GET /doors/{id}/lock_rule`: the status and code, and above all **what a door with no rule answers** (the spike prints `type` and `ended_time` and says when `type` is not a documented value). If a door on site has a rule or an unlock schedule, note what it reads;
   - **(P5.5, read-only)** `GET /doors/settings/emergency`: both flags present and boolean;
   - **(P5.5, listen only)** the notifications WebSocket: that it opens on `wss://<console>:12445/api/v1/developer/devices/notifications` with the same token (it needs the `view:device` scope and Access 1.20.11 or later), and, from the `--unlock` run in step 4, **which events the unlock produced**: is there an `access.data.device.remote_unlock`, is its `data.unique_id` the door id (the spike prints `true`/`false`), and **does anything arrive when the door relocks**. The spike records event names and field names only;
   - while the socket is open (use `--listen 60`), have the person at the door **badge in with a card or PIN** and note whether any frame arrives: the reference does not say whether non-remote unlocks are pushed;
   - whether the console sends anything unprompted on the socket (pings are invisible to the spike; frames are not), and whether the socket stays open for the whole `--listen` window.

   The spike never sends `PUT /doors/{id}/lock_rule` or `PUT /doors/settings/emergency`. Do not send them by hand on site either, unless the site owner asks for it: they change how every door behaves.
6. **Update**, in one change on a task branch:
   - `src/main/access/types.ts`: fix the schemas, and replace "UNVERIFIED (OS-1)" with "verified on Access <version> on <date>" for what was confirmed;
   - `scripts/mock-access/app.ts` / `doors.ts`: match the real statuses, codes, field shapes and relay duration, the real "no rule" answer, and push (or stop pushing) whatever the socket really does (§7.2);
   - `tests/fixtures/access/`: keep the console-captured files (`"_source": "console"`). Check them with `npm run spike:scan -- tests/fixtures/access` and by eye (door names are site data; rename them if they are sensitive). Then `npm test`;
   - `docs/SPEC.md` §5.2 (and R3): replace the community-sourced notes with the verified facts;
   - this document: add an "On-site results" section with the date, Access version and every difference found.
7. Delete `.env.local`'s site token from the laptop when done, or revoke it on the console if it was created only for the test.

### 7.2 The mock's own choices (open for OS-1)

None of the following is in the reference. Each is marked "the mock's own choice" in `scripts/mock-access/app.ts` or `doors.ts`, and OS-1 replaces it with what the console does.

1. **HTTP status per error code.** 400 `CODE_PARAMS_INVALID`, 401 `CODE_ACCESS_TOKEN_INVALID`, 403 `CODE_OPERATION_FORBIDDEN`, 500 `CODE_SYSTEM_ERROR`: all four statuses are in the reference's table and fit its descriptions. **404** (`CODE_NOT_EXISTS`, `CODE_RESOURCE_NOT_FOUND`) and **405** (wrong method) are **not** in that table: a real console may well answer those with 400, 402 or even 200 and an error `code`. The mock keeps them so the client's "any non-2xx or any non-`SUCCESS` code is an error" rule is exercised with several statuses. (413 for a body over 64 KiB is the mock's too.)
2. **Lock-rule interactions**, i.e. what `door_lock_relay_status` reads. First match wins: emergency lockdown → `lock`; emergency evacuation → `unlock`; rule `keep_lock` → `lock`; a momentary unlock running → `unlock`; rule `keep_unlock`, `custom` or `schedule` → `unlock`; otherwise `lock`.
   - **unlock** is momentary (`--unlock-ms`, 5 s), then the relay returns to the door's standing state (so it stays `unlock` under `keep_unlock` / `custom`).
   - **`keep_unlock`**: `unlock` until `reset`, `lock_now` or another rule. `GET` answers `{ type: "keep_unlock", ended_time: 3602128562 }` (a far-future constant).
   - **`keep_lock`**: `lock`, a running momentary unlock is cancelled, and **a remote unlock is refused** with 403 `CODE_OPERATION_FORBIDDEN`. `ended_time` is the same far-future constant.
   - **`custom`** with `interval` minutes: `unlock` until now + interval, then `lock` and no rule. `GET` answers `{ type: "custom", ended_time }`.
   - **`reset`**: ends `keep_lock` / `keep_unlock` / `custom` → no rule. It leaves `schedule` and `lock_early` alone (the reference says reset is not for schedules) and does not cut a running momentary unlock short.
   - **`schedule`** (P5.6): the reference has no call that creates an unlock schedule (it is set up in the Access app), so the mock has a mock-only control for "this door is inside its unlock schedule for the next N minutes" (§7.6). It reads as `unlock`, and `GET` answers `{ type: "schedule", ended_time: <now + N minutes> }` until then, then no rule. The mock keeps one rule per door, so any rule set through the API replaces it.
   - **`lock_early`**: `lock`, and `GET` answers `{ type: "lock_early", ended_time }` until then. `ended_time` is the end of the schedule it cut short when the door was inside one (P5.6), and the next UTC midnight otherwise. A remote unlock still works.
   - **`lock_now`**: ends the rule and a running momentary unlock → `lock`, no rule.
   - A door with `is_bind_hub: false` refuses `PUT lock_rule` with 403 `CODE_OPERATION_FORBIDDEN`, as it refuses unlock.
   - The mock answers `type: "schedule"` only for a door put inside a schedule with the mock-only control (P5.6); until P5.6 it never did.
3. **`GET lock_rule` with no rule** answers `{ "type": "", "ended_time": 0 }`. Undocumented: a guess. The app's schema accepts any `type` string and a missing `ended_time` for this reason.
4. **Emergency.** `lockdown: true` → every door's relay reads `lock` and unlock is refused (403 `CODE_OPERATION_FORBIDDEN`); `evacuation: true` → every door's relay reads `unlock`; both `false` → the doors return to their own state (rules and timers keep running underneath meanwhile). **Both `true`** → 400 `CODE_PARAMS_INVALID`. The `PUT` body must carry both flags.
5. **Whether non-remote unlocks are pushed.** The reference documents `access.data.device.remote_unlock` as "remote door unlock by an admin" and nothing for a card, PIN, face or schedule unlock. The mock therefore pushes **nothing** for the at-the-door unlock of §7.6 unless asked to with `?push=1`.
6. **Whether the socket sends anything on relock.** Nothing documented, so the mock sends nothing: not on relock, not for lock rules, not for emergency mode, not for the door position.
7. Smaller ones: the pushed frame's `event_object_id` is the fake hub id `mock-hub-0001`, `data.up_id` is the door's floor id and the other fields repeat the reference's sample values; the mock sends no WebSocket pings of its own; a plain `GET` of the notifications path without an upgrade answers 400 `CODE_PARAMS_INVALID`; `--fail-rate` applies to REST only, not to the upgrade or the mock-only controls.

### 7.4 Notifications WebSocket

`wss://127.0.0.1:12445/api/v1/developer/devices/notifications`, same Bearer token on the upgrade request. There is no `ws` package in the project: the server side is written by hand on `node:https`'s `'upgrade'` event (`notifications.ts`), with the RFC 6455 framing as pure functions in `ws.ts`. It answers ping with pong, answers a client close with a close, ignores anything else a client sends, and sends unmasked text frames.

> **The only frame the mock ever pushes is `access.data.device.remote_unlock`, on every successful `PUT /doors/{id}/unlock`.** It pushes **nothing when the door relocks**, and no frame carries the relay state, because the reference documents no such event. A client that draws the lock state must read `door_lock_relay_status` with `GET /doors` (or `GET /doors/{id}`): after the push to see `unlock`, and again later to see `lock`. The mock invents no undocumented event.

```json
{
  "event": "access.data.device.remote_unlock",
  "receiver_id": "",
  "event_object_id": "mock-hub-0001",
  "save_to_history": false,
  "data": {
    "unique_id": "<door id>",
    "name": "Front Door",
    "up_id": "<floor id>",
    "timezone": "",
    "location_type": "door",
    "extra_type": "",
    "full_name": "Mock Console - 1F - Front Door",
```

A missing or wrong token fails the upgrade with a plain HTTP **401** and the usual error envelope (`CODE_ACCESS_TOKEN_INVALID`), then the socket is closed: a client should treat that as "stop and fix the token", not as something to retry.

### 7.5 Design changes

- `app.ts` (pure): all routes, `authorizeUpgrade()` (the decision for an upgrade request), `onNotification()` (the frames to push) and the mock-only controls.
- `doors.ts` (pure): the door store with the lock-state model of §7.2, an injectable clock (`now`) next to the injectable timers, and a change hook (`store.onChange`) reporting unlocks (with their source), relay changes, rule, emergency and position changes.
- `ws.ts` (pure): handshake accept key and frame encoder / decoder. `notifications.ts`: the WebSocket hub on a socket. `http.ts`: the `node:https` server (REST + upgrade), which `server.ts` (command line, certificate, token, start-up text) and the tests both use.
- `tests/unit/accessMock.test.ts` covers all of it, including a run over real TLS on an ephemeral loopback port with undici's `WebSocket` through the app's pinned Agent.
- `--port 0` picks a free port; the start-up text prints the port actually bound.

### 7.6 Mock-only controls: "unlocked from elsewhere"

The lock-state feature has to show a door that something other than the app unlocked, e.g. a card tap at the reader. Per the reference that produces **no** WebSocket frame, so the only way to see it is the next `GET /doors`. These routes make it happen. They are **not part of the Access API**: they live outside the API prefix, under `/__mock`, need the same Bearer token, answer in the same envelope (`data` is the door afterwards) with the mock header, and are not subject to `--fail-rate`.

| Route | Effect | Errors |
|---|---|---|
| `POST /__mock/doors/{id}/unlock` | Momentary unlock "at the door" (`--unlock-ms`). **Silent: no WebSocket frame.** Works on a door without a hub | 403 `CODE_OPERATION_FORBIDDEN` under `keep_lock` or lockdown |
| `POST /__mock/doors/{id}/unlock?push=1` | The same, and also pushes the `remote_unlock` frame (for trying the "what if the console does push it" case) | as above |
| `POST /__mock/doors/{id}/lock` | Relock now: ends a running unlock and any lock rule, like `lock_now`. Pushes nothing | |
| `POST /__mock/doors/{id}/position?status=open\|close` | Sets `door_position_status`. Pushes nothing | 400 `CODE_PARAMS_INVALID` for another status |
| `POST /__mock/doors/{id}/schedule[?minutes=N]` | **P5.6.** The door's unlock schedule "has just started": relay `unlock` and lock rule `{ type: "schedule", ended_time: now + N minutes }` until it ends (§7.2). `N` is a whole number from 1 to 1440, default 60. Replaces any rule the door had. Pushes nothing. This is how the Doors screen gets a `schedule` rule to show and its Lock a schedule for `lock_early` to end | 400 `CODE_PARAMS_INVALID` for other `minutes` |
| `POST /__mock/notifications/drop` | Cuts every WebSocket client off without a close frame, to exercise reconnect. `data: { closed: <n> }` | |

### 7.7 Spike and fixtures

- `npm run spike:access` stays read-only by default and now also reads `GET /doors/{id}/lock_rule` (the `--unlock` door, else the first door) and `GET /doors/settings/emergency`, and opens the notifications WebSocket for `--listen` seconds (default 3; `0` skips it). With `--unlock` the socket is opened before the unlock and kept open through the relay watch plus 2 s, so the run records which events an unlock produces and whether anything follows the relock. For each frame it prints and saves the **event name and field names only**. A lock-rule or emergency read that fails, or a socket that does not open, is reported and does not fail the run (older Access versions and narrower tokens have none of them).
- It **never** sends `PUT /doors/{id}/lock_rule` or `PUT /doors/settings/emergency`. Its only write is still the one confirmed unlock.
- New fixtures in `tests/fixtures/access/` (see its README): `lock-rule.json` and `emergency.json` (written by the spike), `lock-rule-custom.json`, `lock-rule-keep-unlock.json`, `lock-rule-set.json`, `emergency-evacuation.json`, `emergency-set.json` (captured from the mock by hand, since the spike does not send those `PUT`s), and the three WebSocket frames `ws-remote-unlock.json`, `ws-doorbell.json`, `ws-doorbell-change.json` (`"_source": "reference"`, ids replaced by fakes).
