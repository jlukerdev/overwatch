## Running it

```bash
npm run spike:video                                   # first connected G4/G5 camera that already has `high`, 60 s
npm run spike:video -- --camera Carport --quality medium --duration 25
npm run spike:video -- --list                         # cameras, existing qualities, codec probe (read-only)
npm run spike:video -- --keep-open                    # leave the window open after measuring (look and listen)
npm run spike:video -- --bare                         # no overlay/clock/audio analyser: player cost only
npm run spike:video -- --trim-keep 0                  # upstream VideoRTC buffer trimming (reproduces the stall below)
```

- **Read-only against the console:** `GET /v1/cameras` and `GET /v1/cameras/{id}/rtsps-stream` only. If the requested quality has no URL, the run exits and lists the qualities that exist. It never POSTs. The API calls are spaced at least 150 ms apart (the 10 req/s limit), and a full `--list` is 10 requests.
- **TLS:** the same TOFU pin as P0.3. `VP_CONSOLE_FINGERPRINT`, else `scripts/spikes/output/console-pin.json`, else trust on first use and save the pin (`scripts/spikes/lib/tls.ts`).
- **Secrets:** `.env.local` is parsed with `util.parseEnv`, **not** loaded into `process.env`, so go2rtc and Electron are started with an environment that has none of its `VP_*` variables. Electron only gets the go2rtc port, the stream name (`spike_<quality>`), paths and the per-launch go2rtc `Authorization` value (see [Security](#security-go2rtc-api-auth-and-listener-ownership)). Every console line goes through the redactor: source URLs, key, host, go2rtc credentials (plain, base64 and any `Basic …` value), home directory, IPs other than 127.0.0.1, ids, MACs.
- **Outputs** (all in the gitignored `scripts/spikes/output/video-spike/`): `result-<platform>-<arch>-<quality>[-bare].json` (no URLs, ids or host; home dir shortened to `~`), a screenshot `.png` taken at the end, and the staged page `app/`. The go2rtc config `go2rtc.yaml` is written there with mode 0600 and **deleted as soon as go2rtc's API answers**. go2rtc keeps it in memory, and the file is also removed on exit or Ctrl+C.

### go2rtc source URL transform (confirmed against the v1.9.15 source)

```
Protect:  rtsps://<console-host>:7441/<16-char alias>?enableSrtp
go2rtc:   rtspx://<console-host>:7441/<16-char alias>
```

- `rtspx://` is go2rtc's TLS RTSP scheme with **certificate verification off** (`internal/rtsp/rtsp.go` registers `rtsp`, `rtsps` and `rtspx`. `pkg/tcp/dial.go` sets `InsecureSkipVerify` when the scheme's 5th letter is `x`, **and also for plain `rtsps://` when the host is an IP address**). go2rtc can't pin a certificate. The launcher only accepts sources whose host equals the console host the API was called on (`sourceHostIs`). That keeps R4's "pinned console host only" in spirit, but the RTSPS leg itself is not pinned.
- `?enableSrtp` is removed (go2rtc README, UniFi note, issue #81). Other query parameters are kept (`toGo2rtcSource`, unit-tested). Without the transform go2rtc can't open the stream. With it, the first frame arrives 0.3–0.5 s after the WebSocket connects.

### go2rtc config shape (redacted)

```yaml
app:
  modules: ["api", "ws", "rtsp", "mp4"]   # mp4 = the MSE WebSocket handler; no webrtc/homekit/srtp/rtmp/…
api:
  listen: "127.0.0.1:<free port>"
  origin: ""                              # go2rtc default: same-origin WebSocket check stays on
  allow_paths: ["/api", "/api/ws", "/api/streams"]   # no web UI, no /api/config, no /api/exit
  username: "vp_<24 random base64url chars>"        # new per launch
  password: "<24 random base64url chars>"           # new per launch
  local_auth: true                        # without this go2rtc skips auth for loopback clients
rtsp:
  listen: ""                              # RTSP server off (the RTSP *client* still works)
log:
  level: "info"
streams:
  spike_high: "rtspx://<console-host>:7441/<alias>"
```

`lsof` during a run: go2rtc's **only listening socket is `127.0.0.1:<port>`**. It also has the loopback connections from Electron and the launcher, and one outbound TCP connection to the console on 7441. No 1984/8554/8555 listeners.

### WebSocket origin (Phase 2 must handle this)

go2rtc's default origin check (`origin: ""`) accepts a WebSocket only when the `Origin` host equals the request `Host`. A page loaded with `loadFile` sends `Origin: file://`, and the electron-vite dev server sends `http://localhost:5173`. Both are rejected. **Don't** set `origin: "*"`: any website open in the user's browser could then connect to the loopback port and watch the cameras. The spike instead rewrites `Origin` to `http://127.0.0.1:<port>` in main (`session.webRequest.onBeforeSendHeaders`), only for `ws://127.0.0.1:<port>/*` and `http://127.0.0.1:<port>/*`. The app should do the same in `streams/`.

## Security: go2rtc API auth and listener ownership

### Per-launch API credentials

Loopback-only is not enough: any local process (or a web page via DNS rebinding or a non-browser client that ignores the WebSocket `Origin` check) could otherwise read `/api/streams` or attach to `/api/ws` and watch a camera. So the go2rtc API now needs Basic auth.

- **What go2rtc v1.9.15 does** (`internal/api/api.go`, confirmed in the tagged source): `api.username` / `api.password` turn on `middlewareAuth`, which wraps the **whole** API handler. That covers `/api`, `/api/streams`, the `/api/ws` WebSocket upgrade (the `ws` module registers through the same mux) and 404s. It uses `r.BasicAuth()` and a plain string compare (not constant-time, which is fine on loopback), and answers `401` with `WWW-Authenticate: Basic realm="go2rtc"`. **Loopback clients are exempt unless `api.local_auth: true`** (`isLoopback` matches `127.*`, `[::1]` and unix sockets). Because the API only listens on 127.0.0.1, `local_auth: true` is required, otherwise the credentials do nothing.
- **Generation:** `createGo2rtcAuth(randomBytes)` in `lib.ts`. 18 random bytes each, base64url, so 24 chars and 144 bits per value, username prefixed `vp_`. base64url has no `:` (Basic auth splits on it) and nothing YAML-special. `buildGo2rtcConfig` refuses anything else. They exist only in launcher memory, in the 0600 config file that's deleted once go2rtc is up, and in go2rtc's memory.
- **Launcher requests** (health check, `/api/streams` stats, `--list` probes) all send `Authorization: Basic …`.
- **Electron main** gets the header value in the env var `VP_SPIKE_GO2RTC_AUTH` (not argv, so it isn't in `ps` args). It reads it and `delete`s it from `process.env` at startup, before any Chromium helper starts, so GPU, renderer and utility processes don't inherit it (checked with `ps -E`: only Electron main still shows it). The existing `session.webRequest.onBeforeSendHeaders` hook for `ws://127.0.0.1:<port>/*` and `http://127.0.0.1:<port>/*` now adds `Authorization` next to the `Origin` rewrite, so **the renderer never sees the credential**: the page still only gets the port and stream name, and VideoRTC opens a plain `ws://` URL. `app.on('login')` cancels any auth challenge, so a wrong header can't turn into a prompt.
- **Env trade-off (spike only):** the initial environment of Electron main stays readable to **same-user** tools (`ps -E`, `/proc/<pid>/environ`) for the life of the process, even after the `delete`. A same-user attacker can also read process memory, so this adds little real exposure, but stdin or an IPC pipe would avoid it. In the app it doesn't arise: go2rtcManager runs **inside** Electron main and generates the credentials itself, so nothing is passed between processes.
- **Redaction:** `scrub()` (all console lines and the result JSON) runs `redactSecrets` with the username, password and base64 token, plus a generic `Basic|Bearer <token>` rule. A live run's console log and result JSON contain no credential.
- **Live check (each run, printed and stored in the result JSON as `go2rtc.authChecks`; the run aborts if any is accepted).** Carport @ low, 2026-11-12:
  ```
  go2rtc auth: REJECTED  GET /api/streams, no credentials -> 401
  go2rtc auth: REJECTED  GET /api/streams, wrong password -> 401
  go2rtc auth: REJECTED  WebSocket upgrade /api/ws, no credentials -> 401
  ```
  Checked by hand during a run as well: `curl http://127.0.0.1:<port>/api/streams` → 401, `curl …/api` → 401, a `curl` WebSocket upgrade → 401, and Node's `new WebSocket('ws://127.0.0.1:<port>/api/ws?src=spike_low')` closes with 1006 without opening. The spike still played (VideoToolbox, 287 frames, audio decoded).

### Free-port race

`freeLoopbackPort()` binds port 0, reads the port and closes the socket before go2rtc binds it. In between another local process can take the port. go2rtc then only logs `[api] listen` with an error and **keeps running without a listener**, and the impostor would get every request, including our credentials and the player's WebSocket.

After go2rtc starts, `startGo2rtc` collects three facts and `decideOwnership()` (pure, unit-tested) decides:
1. `GET /api` **with** our credentials → must be 200. Any other answer from the port means it isn't ours, and the launcher stops waiting at once instead of timing out.
2. `GET /api` **without** credentials → must be 401 (proves auth is enforced).
3. **Listening PID** must be the child's PID and nothing else: `lsof -nP -iTCP:<port> -sTCP:LISTEN -Fp` on macOS/Linux, `netstat -ano -p TCP` on Windows.

The PID check is the real guard: the auth checks only stop an impostor that enforces auth. An impostor that answers 200 to everything still fails check 2, and an impostor that copies go2rtc's 401 behaviour still fails check 3. **On macOS/Linux the PID check is mandatory** (lsof unreadable → fail). **On Windows it's best effort:** if `netstat` can't be run or parsed, the auth checks alone decide, and a PID that doesn't match still fails. If the decision fails, the launcher kills the child, deletes the config and retries on a new port, up to 3 attempts. The live runs logged `listener PID <pid> is our go2rtc child`. The race itself was not reproduced live, only in the unit tests.

### Carry into P2.1 `streams/go2rtcManager.ts`

- **Per-launch credentials:** generate a new random username/password (`crypto.randomBytes`, base64url) every time go2rtc starts. Write `api.username`, `api.password` and **`api.local_auth: true`** into the config (0600 in userData, or delete it after start). Never persist or log them, and add them to the main-process log redactor.
- **Header injection in main:** add `Authorization: Basic …` in the same `session.webRequest.onBeforeSendHeaders` hook that rewrites `Origin`, filtered to `ws://127.0.0.1:<port>/*` and `http://127.0.0.1:<port>/*` only. The renderer and the IPC payloads only get the port and stream names. Handle `app.on('login')` so a challenge never prompts. All of main's own go2rtc calls (health, `/api/streams` codec probe for R7) send the header too.
- **PID verification:** after start, require authenticated 200 + unauthenticated 401 + listener PID == child PID (`lsof` on macOS, `netstat -ano`/`Get-NetTCPConnection` on Windows), retry on a new port up to 3 times, and surface a clear error if all fail. Reuse `decideOwnership`, `parseLsofPids` and `parseNetstatListenPids` from the spike. Re-run the check after any go2rtc restart.

## Finding: VideoRTC's 5 s buffer trim stalls Protect `high` (fixed in the spike, needed in P2)

With upstream VideoRTC behaviour (`--trim-keep 0`), `high` stalls after about 4.4 s: the decoded frames freeze at about 130, Chromium logs `video DEMUXER_UNDERFLOW`, audio keeps playing, and VideoRTC keeps seeking forward and setting `playbackRate` up to 5. It recovers briefly once per keyframe and then stalls again. `medium` and `low` are not affected.

**Cause:** Protect's `high` stream has a keyframe every **5.0 s** (append sizes > 100 KB at 0.4, 5.5, 10.4, 15.5, 20.5, 25.4 s). VideoRTC's `updateend` handler calls `sb.remove(buffered.start, buffered.end − 5)`. Under the MSE coded-frame-removal rules this **also removes every frame up to the next keyframe**. With a 5 s GOP that removes the frames still being played, so the video track runs dry. go2rtc delivered every packet (0 drops) and no `appendBuffer` threw, so the fault is in the player.

**Spike workaround (default `--trim-keep 15`):** the page wraps `SourceBuffer.prototype.remove` so that it never removes anything within 15 s of the buffered end (VideoRTC itself is unmodified). With it, `high` plays at 30 fps for 60 s with 0.06% dropped and the same ~1.0 s latency.

**For P2 (`LivePlayer`):** subclass `VideoRTC` and override `onmse()` so the kept window is at least 2× the longest GOP (15 s covers Protect's 5 s), or so it trims only up to the last keyframe before `currentTime`. Keep the vendored file unmodified. Memory cost at `high`: about 2 Mbit/s × 15 s ≈ 4 MB per player.

## Problems hit

1. **Carport (and every camera with streams) was H.264** in the first runs, which blocked the H.265 half of G0. Resolved by turning on Enhanced Encoding (see Verdict and "H.265 re-run").
2. **go2rtc rejects `Origin: file://`**, so the spike rewrites the header in main (see above).

5. **`getAppMetrics` CPU is machine-normalized**, and on macOS the GPU process is `Electron Helper --type=gpu-process`, not `Electron Helper (GPU)`. The spike labels processes from `ps … args`.
6. **The fixture sanitizer's IPv4 rule mangles Chrome and driver version numbers**, so the result JSON is scrubbed with targeted rules instead (no secrets are put into it in the first place).
7. **`ELECTRON_RUN_AS_NODE=1` from VS Code** made the spawned Electron run as Node on the Windows run; the launcher now strips it (see "Windows run").

## Windows procedure (for the user)

**Prerequisites**
1. Node **24** (`node -v` → v24.x) and Git.
2. In the repo, on this branch: `npm ci`. This installs Electron through `postinstall`.
3. `npm run fetch:go2rtc` installs `resources\bin\win32-x64\go2rtc.exe` (or `win32-arm64`) and checks its SHA-256.
4. Create `.env.local` in the repo root with `VP_CONSOLE_HOST=<console IP or host>` and `VP_PROTECT_API_KEY=<key>`. Optionally add `VP_CONSOLE_FINGERPRINT=<SHA-256>` to pin the console certificate (copy it from `scripts/spikes/output/console-pin.json` on the Mac). Without it the first run trusts on first use and saves the pin.
5. The PC must reach the console on 443 and 7441 (same LAN). Up-to-date GPU drivers. Chromium decodes HEVC through D3D11 and should not need the Microsoft Store **HEVC Video Extensions** (not verified here), but note whether they are installed.

**Run** (PowerShell, repo root). Use the same camera as on the Mac, once Enhanced Encoding is on:
```powershell
npm run spike:video -- --list
npm run spike:video -- --camera Carport --quality high --duration 60
npm run spike:video -- --camera Carport --quality low --duration 25
npm run spike:video -- --camera Carport --quality high --duration 30 --keep-open   # look and listen, then close the window
```
`--list` must show `video H265` for the camera, otherwise the run can't prove G0. A Windows Firewall prompt should **not** appear (go2rtc only listens on 127.0.0.1). If one does, deny it and report it.

**Pass/fail.** The summary block ends with five PASS/FAIL lines and `G0 (win32) PASS|FAIL`. Pass needs all of these:
- `MSE mime` contains `hvc1` or `hev1` (`H.265 over MSE`),
- `video decoder` is a platform decoder: expect `D3D11VideoDecoder` (or another non-FFmpeg platform name) with `platform=true`. `FFmpegVideoDecoder` / `platform=false` is a fail. Chromium has no software HEVC decoder, so HEVC frames decoding at all already implies hardware,
- `gpu video_decode enabled`,
- `audio decoded` with a non-zero byte count, and you can hear the camera with `--keep-open`.

If H.265 fails, R1's fallbacks apply (SPEC §7).

**Send back:** the console output of the three runs (it is redacted, but check it for anything that looks like your console address before sharing), and `scripts\spikes\output\video-spike\result-win32-*-high.json` and `…-low.json` (no URLs, ids or host; the home directory is shortened to `~`; it includes GPU vendor/device ids and driver info). Also send the GPU model and driver version, and whether HEVC Video Extensions are installed. Don't send `.env.local`, `console-pin.json` or anything else from `scripts\spikes\output\`.

## Consequences for Phase 2

- **R1 (H.265 over MSE):** **macOS confirmed with a real H.265 stream** (hvc1 over MSE, VideoToolbox platform decoder, all three qualities). **Windows: hardware decode (D3D11) and MSE playback confirmed on H.264, HEVC capability probes positive, real H.265 stream not tested (waived by the user for G0).** Keep a residual R1 note: the first Phase 2 run on Windows with an H.265 camera should confirm `D3D11VideoDecoder` on hvc1, and the R7 "codec unsupported" state covers it if not. Watch the macOS `high` drop rate (see "H.265 re-run").
- **R7 (codec detection):** two clean hooks were found.
  1. **Before attaching a player:** `GET /api/streams?src=<name>&video=all&audio=all` on go2rtc runs a probe consumer. It opens the upstream, returns the producer `medias` (e.g. `video, recvonly, H264`) and detaches. Main can do this when it registers a stream (QUAL-8) and send the renderer `{ codec: 'h264' | 'h265' }`. The renderer then checks `MediaSource.isTypeSupported('video/mp4; codecs="hvc1.1.6.L153.B0"')` and shows "codec unsupported" instead of a black cell. `--list` uses exactly this.
  2. **In the player:** VideoRTC's `mseCodecs` (go2rtc's `{"type":"mse"}` answer) carries the negotiated mime. If the browser offered no HEVC codec, go2rtc answers with an error message instead, and `LivePlayer` should map that to the same state.
- **Stream switching (QUAL-4/5, fill mode):** the first frame takes 0.3–0.5 s on a fresh upstream, because go2rtc opens RTSPS lazily and the camera starts with a keyframe. **Not measured:** a second player joining an upstream that is already running probably waits for the next keyframe, which can take up to **5 s at `high`**. P2 should measure this (two players on one stream) before relying on "the old player stays visible until the new one fires `playing`". The pre-warm idea in ARCHITECTURE §3 matters more at `high`.
- **Player buffer:** override VideoRTC's trim (see Finding). Its playback-rate control holds about 1 s of buffer, and that can be tuned down in P2.5 if glass-to-glass needs it.
- **Security settings to carry into `streams/go2rtcManager.ts`:** `app.modules: [api, ws, rtsp, mp4]`, `api.allow_paths`, `rtsp.listen: ""`, loopback `api.listen`, the Origin rewrite in main, the config file 0600 in userData (or deleted after start), child processes without secrets in their environment, and per-launch API credentials with `local_auth: true`, the `Authorization` header added in main, and listener PID verification (see [Carry into P2.1](#carry-into-p21-streamsgo2rtcmanagerts)).
- **Audio:** cameras send AAC 16 kHz mono plus Opus 48 kHz. go2rtc picks AAC for MSE, which plays fine. Mute per cell is just `video.muted`.
- **Measurement:** use `ps`-style per-process CPU or multiply `getAppMetrics` by the core count in the P2.5 harness. The CDP Media domain via `webContents.debugger` works without opening a remote-debugging port.
